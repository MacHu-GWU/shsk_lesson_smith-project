# Spec 文件格式约定

这个文件只在编写 lesson-smith skill 本身时参考. SKILL 运行时不引用它.

每个特殊文件的规范是一个**目录**, 里面每个语种两份文件.

---

## 1. 一个 spec 目录长什么样

```text
00-common/02-readme-original-spec/
  readme-original-cn-spec.md         规范. 权威在这.
  readme-original-cn-template.md     骨架. 原样复制.
```

- **目录名不带语种后缀**, 形如 `NN-<特殊文件名>-spec/`.
- **文件名带语种**, 形如 `<特殊文件名>-<lang>-spec.md` 与 `<特殊文件名>-<lang>-template.md`.
- **不放语料库.** 早先每个 spec 目录下挂一个 `corpus/`, 收几份已发布 repo 的同类文件当参照. 那套东西大半是为了校准英文重写的语感, 翻译砍掉之后它的主要用途没了, 剩下的那点参照价值抵不上每次都要判断 "该读哪一份, 读几份" 的开销. 规范和 template 说清楚就够, 要看真实写法直接去看已发布的 repo.

**一个 spec 目录里可以放不止一个语种**, 例如:

```text
02-upskill/forge/docs-upskill-learn/
  docs-upskill-learn-spec.md            英文规范
  docs-upskill-learn-template.md        英文骨架
  docs-upskill-learn-cn-spec.md         中文规范
  docs-upskill-learn-cn-template.md     中文骨架
```

上面那层 `forge/` 是**分组目录**, 把同一个消费者 (这里是 `lesson-smith-upskill-forge`) 要读的东西收在一处, 不是 spec 目录. 它不改变 "一个 spec 一个目录" 这条规矩, 只是在它外面加了一层. 特化层文件多起来之后会有这种分组, 不要把它压平.

---

## 2. 两份文件的分工

**spec**: 普通 markdown, 不是注释. H2 从 1 连续编号, 之间用分隔线隔开, 该用表格就用表格. 所有规范性文字 (定性, 适用范围, 结构, 字段约束, 写作原则, 语料怎么用, 交付前自检) 都在这里.

**template**: 纯骨架. frontmatter 加 `[方括号]` 占位内容, 结构就是真实的 markdown 结构. **一个注释都没有.** 起草时整份复制过去填空, **复制完不用删任何东西**.

spec 开头点名它配套的 template; template 不反向引用 spec (它要能被原样复制).

---

## 3. 为什么不把规范塞进顶部注释

早先的写法是一个文件: 规范全部写在顶部一个 `<!-- ... -->` 里, 正文即模板, 产出时把注释整段删掉. 它有一个真实的好处 (模板和规范贴身), 但代价比好处大得多:

- **比例失衡.** 实测下来注释 171 行, 模板 13 行. 那不是 "模板配了段说明", 是一份规范文档顶了个模板的帽子.
- **`---` 用不了.** 两个以上连字符会截断 HTML 注释, 所以没有分隔线, 只能拿 `== 标题 ==` 凑, 而那东西没有任何工具认识.
- **整段渲染成空白.** 预览里什么都看不到, 表格, 加粗, 链接全是死的, 人和 AI 读到的都只是裸文本.
- **没有 heading 就没有折叠, 没有大纲, 没有锚点**, 别的 spec 想引用其中一节也链不过去.
- **多一个可以漏掉的步骤.** "复制之后记得删注释" 是会被漏的, 而漏了的后果是产出的文档里夹着整份规范. 拆开之后这一步不存在.

至于原来那条 "合在一起可以避免漂移", 实测没兑现: 受控词汇在注释里写一遍, 在模板里又写一遍, 同一个文件里已经在重复了. 合并防不住漂移, 只是把两处凑近了点.

---

## 4. 哪些文件分语种

**判据只有一条: 带 template 的分, 不带的不分.**

- **带 template 的分** (`02` 到 `06` 那几个 spec 目录). template 本身就是那个语种的文本, 复制过去就变成中文文档, 它必须分; spec 跟着分, 理由见下一节. 受控词汇表这类东西也就自然落在分开的这一侧.
- **不带 template 的不分** (`01-repo-layout`, `07-syllabus-spec`, `08-series-converge-spec`, `09-root-docs-spec`, `10-ship-spec`). 它们描述的是 "长什么形状" 与 "做什么", 换个语种照样成立.

流程类规范值得单独说一句. 统稿是中文统中文, 英文统英文, 但**那是跑的时候的参数, 不是分文件的理由**: 一份写着 "一次只统一个语种" 的文件, 严格优于两份只差后缀名的文件.

---

## 5. 分了的, 每个语种各写一套

一个语种一份 spec 加一份 template, 各写各的, 不是同一份的翻译. 两条理由:

- **受控词汇本来就不同.** 中文的 `## 2. 要做的事情` 和英文那一行是两个字符串, 各自钉死在各自的 spec 里最省事.
- **用中文描述英文该怎么写, 是 chinglish 的最大来源.** 照着一份中文提纲写英文正文, 每一节都会带着中文的句式落地. 英文版的 spec 就该用英文写.

目前只有中文版. 英文版属于多语种模块, 还没做, 所以中文 spec 里不写任何 "英文版专属" 的规则.

---

## 6. 写一份新 spec 的顺序

先去读真实写过的同类文件, 再从里面归纳规范, 最后才写 template. 展开见 [ref/ref-maintainer-README.md](ref/ref-maintainer-README.md) 第 5 节.
