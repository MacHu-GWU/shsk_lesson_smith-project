# quiz 出题指南, 题型与写法

**适用范围**: 写 quiz 题库 (`examples/NN-prove-i-get-it/README-cn.md`) 时的参考, 与 [quiz-readme-cn-spec.md](quiz-readme-cn-spec.md) 配套. upskill 与 showcase 共用, 正文不带类型名, 落地时无需替换.

**这份指南是推荐, 不是强制.** 题库硬的只有 spec 里的四段结构和出处要求. 题型怎么混, 场景题占多少, 口吻偏哪边, 都看这门课自己的内容: AI 读完课程材料给建议, 创作者拍板. 下面的东西是帮你判断和下笔的, 不是要你全都用上.

---

## 1. 三种题型

| 题型 | 长什么样 | 适合什么内容 |
| :--- | :--- | :--- |
| 场景加证据题 | 一段情境, 一份真实的代码, 命令, 输出或报错, 再分点提问, 每问有确切答案 | 有现象可看的内容: 读输出, 排查, 事故与后果, 原理落到具体文件或字段 |
| 短概念题 | 一两句话的问法, 答案确定 | 纯定义, 命名, 规则, 边界, 例如 "`.gitignore` 的作用是什么, 已被跟踪的文件加进去会怎样" |
| 讨论题 | 打开一个话题, 期待几句话把 what 和 why 讲清 | 答案不唯一的取舍与设计理由, 例如 "为什么选 A 不选 B" |

三种题**可以在同一本题库里混用**. 判断的标准不是题干长短, 而是**指代是否清楚, 答案是否可以被核对**. 场景题只是让这两点更容易成立, 不要为了显得有场景硬凑一个.

---

## 2. 怎么定比例和调性

**没有固定比例.** 按这门课的内容性质来:

| 课程的内容偏向 | 题型倾向 |
| :--- | :--- |
| 操作多, 有命令, 有日志, 有报错可看 (云, 运维, 数据库, 构建工具) | 场景题可以占多数 |
| 概念与规则多, 输出不多 (协议, 语言语义, 设计原则) | 短概念题与讨论题占多数, 场景题挑几个关键现象 |
| 偏设计与取舍 (架构, 方法论) | 讨论题占多数, 用场景题把抽象原则落到案例上 |

**流程是 AI 建议, 创作者拍板.** 规划阶段 (第 7 步), AI 扫完全部教学材料后, 在 `examples/_lm-quiz-plan.md` 里给出建议的题型组合和理由, 再和创作者讨论锁定. 场景题需要先找到真实证据才能写, 所以规划时顺便记下每道场景题的证据打算取自哪个文件或哪段输出.

## 3. 场景加证据题怎么写

**把学生放进一个具体的现场, 给他看现场留下的证据, 再分点问几个各有标准答案的问题.**

和简短概念题的区别:

| | 简短概念题 | 场景加证据题 |
| :--- | :--- | :--- |
| 题干 | "说说 Git rebase 和 merge 的区别" | 一段情境, 一份命令或输出, 再问 |
| 学生的负担 | 要猜 "面试官想听哪个角度" | 只要读懂现场, 答案自然在里面 |
| 答案 | 开放, 谁都能说得通 | 唯一, 可以逐点对答案 |
| 检验的是 | 背没背过定义 | 能不能把知识用到眼前的现象上 |

题干的四个部件:

1. **情境** (1 到 2 句): 谁, 在做什么, 做了哪一步操作. 让题干里的每个 "这个", "那个" 都有指代.
2. **证据** (可选但强烈建议): 一小段真实的代码, 配置, 命令输出, 报错. 越像学生亲手见过的越好. 只留和问题相关的几行.
3. **分点提问** (2 到 4 个): 用 (1) (2) (3) 编号, 每一问都有确切答案.
4. **不问 "谈谈", 不问 "有什么好处"**: 每一问落在一个具体的东西上, 例如原理, 文件名, 字段, 数字, 报错原因, 某条命令.

证据放进题干时, 整个 "问题" 段仍是一个 blockquote, 代码块写在 blockquote 里面.

**考察点**写成: 这题在验证哪个心智模型, 并点出答案的确切形态 (例如 "答案是一个文件名和一个原因").

**参考回答**和分点一一对应, (1) (2) (3) 各一句, 学生可以拿去逐条打勾.

## 4. 四个领域的场景题示例

例子刻意取自不同技术领域, 与具体课程无关.

### 4.1 Git, 读输出题

> 同事在 `main` 上执行了 `git reset --hard HEAD~2`, 然后发现丢了两次提交. 他运行 `git reflog`, 看到:
>
> ```text
> a1b2c3d HEAD@{0}: reset: moving to HEAD~2
> 9f8e7d6 HEAD@{1}: commit: fix login bug
> 4c5d6e7 HEAD@{2}: commit: add login page
> ```
>
> 请回答: (1) 被丢掉的两次提交现在还在不在, 依据是什么? (2) 要把 `main` 恢复到 "fix login bug" 那一刻, 该敲哪条命令? (3) 这些提交最终会在什么情况下真正消失?

考察点: reflog 记录 HEAD 的移动历史. 答案是 "还在", `git reset --hard 9f8e7d6`, 以及 "垃圾回收清理过期且不可达的对象之后".

### 4.2 SQL, 场景加现象题

> 订单表 `orders` 有 2000 万行, 慢查询日志里反复出现:
>
> ```sql
> SELECT * FROM orders WHERE DATE(created_at) = '2025-03-01';
> ```
>
> `created_at` 上已经建了索引, 但 `EXPLAIN` 显示 `type: ALL`. 请回答: (1) 为什么索引没有被用上? (2) 改写成什么形式可以命中索引? (3) `type: ALL` 意味着什么?

考察点: 对索引列套函数会使索引失效. 答案是 "对列做了函数运算", `created_at >= '2025-03-01' AND created_at < '2025-03-02'`, "全表扫描".

### 4.3 Docker, 原理加文件题

> 一个 Python 服务的 Dockerfile 里, `COPY . /app` 写在 `RUN pip install -r requirements.txt` 前面. 团队发现: 只改了一行业务代码, 每次构建都要重新下载全部依赖, 耗时四分钟. 请回答: (1) 根本原因是镜像分层的哪条缓存规则? (2) 应该怎样调整这两行的顺序, 或先复制哪个文件? (3) 还应该新增哪个文件来避免把 `.git` 和虚拟环境复制进镜像?

考察点: 某一层的输入变了, 它和它之后的所有层缓存全部失效. 答案是 "上层内容变化使下面的层缓存失效", 先只 `COPY requirements.txt`, 再 `pip install`, 最后 `COPY .`, 以及 `.dockerignore`.

### 4.4 HTTP 与缓存, 事故加后果题

> 某公司的内部跳转服务, 有人把响应状态码从 302 改成 301 上线. 一个月后目标网址换了, 运营在后台更新了映射, 但访问过的员工仍被带去旧地址, 清了服务端缓存也没用. 请回答: (1) 301 与 302 的语义差别是什么? (2) 为什么问题出在员工自己的浏览器上, 而不是服务端? (3) 若要保留 "可以随时改目标" 的能力, 应该用哪个状态码?

考察点: 永久重定向会被客户端缓存. 答案是 "永久搬家 与 临时跳转", "浏览器记住了 301 并不再询问服务器", 302.

## 5. 短概念题与讨论题怎么写

**短概念题.** 一两句话, 答案确定, 指代清楚. 问法落在一个具体的东西上. 参考回答一两句, 考察点直说 "考的就是题面", 不强行拔高.

**讨论题.** 打开一个话题, 期待 3 到 5 句的回答, 里面点明去 repo 的哪里核实, 并讲清背后的原理. 适合答案不唯一的取舍. 参考回答写成 what 加 why, 深入解读把取舍讲透.

两种题的 "问题", "考察点", "参考回答", "深入解读" 四段结构和场景题完全一样, 区别只在 "问题" 段的写法.

---

## 6. 好题的自检清单

- 去掉题干里所有的 "这个", "那个", 学生仍知道指的是什么吗? (指代清楚)
- 每一问的答案, 出题人能在 repo 里指出唯一的出处吗? (可溯源)
- 场景题: 两个懂行的人独立作答, 会得出同样的结论吗? (答案唯一)
- 有没有 "谈谈", "简述好处", "你怎么看" 这类无法打分的问法? 有就改成落在具体对象上. (讨论题是例外, 它本来就是开放的, 但要有参考回答可对照)
- 证据是真的吗? 输出, 报错, 数字要来自 repo 实测或教程正文, 不能凭空捏造.
- 题干有没有长到需要三遍才读懂? 情境不超过两句, 证据只留和问题相关的几行.
- 一本题库里三种题型的组合, 是创作者看过并认可的吗?
