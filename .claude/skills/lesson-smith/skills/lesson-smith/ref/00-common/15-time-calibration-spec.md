# 时间梳理规范

`examples/` 全部写完并统稿之后, 横着比一遍全部 Task, 把六档预计用时分配到位.

**适用范围**: readup, upskill, showcase 三类. evolve 没有 `examples/` 这一层, 也没有 "一门课的总时长" 可言, 不适用.

**位置**: 统稿之后, 写根目录文档之前. upskill 与 showcase 排在锻造之前, 理由见第 1 节.

---

## 1. 为什么单独一步

**统稿定的是内容, 这一步定的是刻度.** 统稿看的是术语一不一致, 承上启下断没断; 这一步看的是每个 Task 的分量, 以及它们摆在一起对不对得上. 两件事用的是同一次通读, 但判据完全不同, 混在一起做, 后一件必然被前一件挤掉.

**必须在全部 Task 齐了之后.** 索引, quiz, demo, 收尾这些位置固定的 Task 也算数, 少一个总和就是残缺的. 这也是它不能提前到写主线那会儿的原因: 一篇篇孤立地估, 估出来的是绝对值, 而学生真正感觉得到的是相对刻度, 横着比才拿得到.

**必须在写根目录文档之前.** 根 TICKET 的预计用时是各 Task 的机械加总 (见 [04-task-ticket-spec](04-task-ticket-spec/task-ticket-cn-spec.md) 第 8.1 节). 各 Task 的档位没定, 那个和就没法算.

**upskill 与 showcase 排在锻造之前**: 这一步要回头改 `examples/` 下的 TICKET, 属于 examples 阶段的收尾. 放在锻造之后, 等于 forge 已经把 examples 当定稿素材跑完了, 又回去动它. `examples/` 定稿只该有一个时间点.

**接着统稿那个 session 做.** 统稿刚把全系列通读了一遍, 这一步要的正是同一次通读的记忆. 另开 session 就是把同一批内容再读一遍.

---

## 2. 先出一张汇总表

按编号顺序读 `examples/` 下每个 Task 的 `README-cn.md` 与 `TICKET-cn.md`, 列成一张表. 六列写死:

| 列 | 填什么 |
| :--- | :--- |
| `NN-title` | Task 目录名, 按编号顺序, **一个都不许漏** |
| 讲什么 | 直接抄它 README 的 frontmatter `description`, **不要自己重新概括** |
| 目前是 | 那份 TICKET 现在写的预计用时, 逐字照抄. 还没写就写 "缺" |
| 建议 | 建议改成哪一档, 写成档位的逐字形式 |
| 增减 | `不变` / `增` / `减`, 三选一 |
| 为什么 | 一句话. 建议不变也要给一句 |

**"为什么" 那一列是这张表的价值所在.** 只有档位没有理由, 创作者没法判断你是不是估错了, 只能凭感觉点头. 理由要落在验得了的东西上: 有几个练习要跑, 要不要装环境, 中间要不要调试, 阅读量有多大. "这一节比较难" 不是理由.

表出完, **紧接着把六档表原样贴一遍** (见 [04-task-ticket-spec](04-task-ticket-spec/task-ticket-cn-spec.md) 第 8 节). 创作者记不住 "第 4 档" 是多少分钟, 让他为了回你一句话去翻规范, 是这一步最容易劝退的地方.

最后给两个数: 当前总和, 以及按你的建议改完之后的总和 (下限加下限, 上限加上限). 创作者要一眼看出这次调整把整门课推到多长.

---

## 3. 人类拍板, 不可跳过

**AI 只出建议, 档位由创作者定.** 这和 README-ORIGINAL 那两个字段是同一个性质的 gate.

创作者会用自然语言回你, 形如 "01 到 03 都给 2 档", "07 我觉得偏重, 上 5 档", "其它照你的建议来". **按档位号说话是预期的**, 不要求他写出分钟数.

- **他说档位号, 你换算成逐字写法.** "3 档" 就是 `15 到 30 分钟`, 不是 `15 到 25 分钟`.
- **他没点到的行按你的建议办**, 但动手前说一句 "剩下这几行我按建议改了", 别默默改.
- **他给的档位和你的建议冲突, 照他的.** 内容的分量他比你清楚, 你只提供刻度和一致性.

拍板之后才动文件.

---

## 4. 改回文件

逐个改 `examples/NN-title/TICKET-cn.md` 第 2 节末尾那一行, **只改那一行**, 别顺手改别的. 内容的事统稿那一步已经过了.

改完复核:

- 每一行都逐字等于六档之一, 全仓 grep 不该找出第七种写法
- 位置固定的那几个 Task 没被漏: 索引在档 1 或档 2, quiz 与 demo 通常是 `30 到 60 分钟`
- 有 Task 顶到档 6 还嫌紧, **提出来让创作者考虑拆**, 不要写成 `120 到 180 分钟`. 上限 120 分钟是硬的

**报一个最终总和给创作者**, 形如 `385 到 700 分钟 (约 6.5 到 11.5 小时)`. **这个和不落盘**: 各 TICKET 才是权威, 写根目录文档那一步会照它们重新加总一遍, 多存一份迟早对不上.

---

## 5. 什么时候算过

- `examples/` 下每个 Task 都有预计用时, 且都落在六档之一
- 每一档创作者都点过头, 没有 AI 单方面定的
- 最终总和已经报给创作者
