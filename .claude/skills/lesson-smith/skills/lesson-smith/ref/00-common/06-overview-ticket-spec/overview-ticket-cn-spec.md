# 索引 Task 的 TICKET 规范, 中文版

**适用范围**: `examples/01-<title>/TICKET-cn.md`, 也就是 examples 下那个索引 Task 的任务卡片. 位置固定在 01, 目录名随课程而定 (`01-overview` 只是推荐). readup, upskill, showcase 三类都有; evolve 不适用.

**配套骨架**: [overview-ticket-cn-template.md](overview-ticket-cn-template.md).

**只管中文版**: 英文版另有一套, 属于多语种模块, 现在还没做.

---

## 1. 它为什么存在

**Task 必然成对.** 索引 Task 也是 Task, 所以它有 TICKET, 不因为它轻就例外.

它的正当写法是**承认它轻**, 而不是硬凑出一份看着很重的验收清单.

---

## 2. 它轻在哪

这个 Task 的活就是**读完那张地图**, 没有产出物, 没有要跑的命令.

- 第 2 节 "要做的事情" 通常就两三条, 而且都是读.
- 第 3 节 "检查清单" **3 到 4 条**, 下限 3 上限 4, 两头都别破.
- **下限那一条不许靠删凑.** 前两条 (说得出分块, 说得出起点) 是死的, 第三条要按这门课的实际情况填一句能当场判定的, 不是可选项.

通用 spec 里 "检查清单常见 5 到 9 条" 那一条**在这里不适用**, 这是明确的例外. 一个只需要读一遍的 Task 硬写出 7 条检查项, 每条都会是注水的.

检查项就照 "你能不能说出来" 写, 例如: 你能说出这门课分成哪几块; 你能说出你打算从哪一块开始, 为什么. 判据是能不能当场答出来, 不是有没有产出文件.

---

## 3. 其余照 Task TICKET 的通用规矩

三段式与受控词汇 (`## 1. 目标` / `## 2. 要做的事情` / `## 3. 检查清单` / `**预计用时:**`), H1 字符集, frontmatter `description` 的形态与长度, **禁止相对路径链接**, 全部照 [04-task-ticket-spec](../04-task-ticket-spec/task-ticket-cn-spec.md), 这里不重复.

最后那条在这一份上尤其容易犯: 它的 README 里全是指向兄弟 Task 的链接, 顺手就想在 TICKET 里也链一个. **不行**, TICKET 会进 GitHub Issue, 相对路径在那里点不动, 提到别的 Task 一律用文字.

---

## 4. 交付前自检

- 检查清单 3 到 4 条, 没有为了凑数注水
- 每条都是 "能不能当场说出来", 没有编造产出物
- 全文没有相对路径链接
- 预计用时那一行在, 且数字是读一遍地图的量级
