# README-ORIGINAL 规范, 中文版

**适用范围**: 四类 repo (readup, upskill, showcase, evolve) 根目录的 `README-ORIGINAL-cn.md`. 四类同形, 所以这一份放在 `00-common` 下.

**配套骨架**: [readme-original-cn-template.md](readme-original-cn-template.md). 起草时把它整份复制过去填空, 里面没有任何注释, **复制完不用删任何东西**.

**只管中文版**: 英文版另有一份 spec 和一份 template, 属于多语种模块, 现在还没做. 所以本文件里不会出现任何 "英文版专属" 的规则. 那些规则不是不要了, 是不该由一份中文 spec 来带 (用中文描述英文该怎么写, 恰恰是 chinglish 最大的来源).

---

## 1. 它是什么

**这不是教学文档.** 它是这个 Repo 面向 GitHub 的普通对外 README, 和其他任何开源仓库的 README 一样.

它是 **Lesson 级** (整个 Repo) 的介绍: 一个 Repo 就是一门 Lesson, 这份文件的 frontmatter 就是这门 Lesson 的门面. 学生学完把 Repo 当作自己的作品时, 别人第一眼看到的也是它.

最容易混的是它和 Repo 根目录那份 `README-cn.md` 的关系. 两段都写给学生看, 区别在海拔:

| | `README-ORIGINAL` 的 description | 根 `README` 的 description |
| :--- | :--- | :--- |
| 海拔 | Lesson, 整个 Repo | Task, 某个 branch |
| 会进哪个索引 | org 级课程索引, 可能几百个 Repo | 本 repo 的 SYLLABUS |
| 读者 | 还没进门的冷读者 | 已经进门的人 |
| 回答什么 | 为什么值得学, 学完有什么收获 | 你将学到什么 |
| 能不能罗列知识点 | **绝对不行** | 反而是对的 |

在 upskill, showcase, readup 里只有一个 Task, 两者 scope 几乎重叠, 但上面这个分工不变, **两边别互相抄**. 在 evolve 里一个 Repo 多个 Task, 两者本来就明显分开. 根 README 那一份的精确定义见各类型自己的 readme spec.

---

## 2. 生命周期, 以及为什么这份要重写两次

- **第一版是种子稿.** 创作最早期就写一版粗稿, 作为后面所有内容生长的种子.
- **第二版是重写.** 种子稿往往和最终写出来的 examples 对不齐, description 也太粗, 撑不起一门 Lesson 的介绍. 所以 examples 全部完工并统稿之后, 在写根目录文档那一步**整份重写** (正文加 description 加 github_about), 让它和成品对齐.

**重写这一步有一道人类 gate, 不许 AI 单方面定稿.** description 与 github_about 是这门课的门面, 一句话决定别人点不点进来. 写完初稿必须停下来交给课程作者过目: 把两个字段摆出来 (拿不准时给两三个不同侧重的候选让他挑), 问他 ok 不 ok, 哪里要调, 按他的意见改完再往下走.

正文那三段不需要这道 gate, 只有这两个字段需要.

## 4. frontmatter, 两个字段

### 4.1 两个字段面向两种人

分清这一点是写好它们的关键.

- **`description` 写给学生**, 也就是要来学这门课的读者.
- **`github_about` 写给老师**, 也就是课程作者本人或其他授课老师.

两句都短, 合起来就是这个 repo 在课程索引里的那一行.

### 4.2 长度

中文版这一档:

| 字段 | 下限 | 上限 |
| :--- | ---: | ---: |
| `description` | 200 | 400 |
| `github_about` | 无 | 150 |

单位是字符, 只算包裹的双引号里面的内容. 形态约束 (一行, 双引号包裹, 哪些字符禁用) 与英文那一档的数字都在 [01-repo-layout.md](../01-repo-layout.md) 第 6 节, 那里是权威, 这里不重复.

- **下限很松, 而且没有任何工具检查它.** 它只用来挡明显敷衍的一句话交差, lint 只卡上限. 概述, 动机, 收获三件事都认真写清楚, 自然就过线, 不需要盯着字数.
- **上限是 lint 卡死的硬线, 但不必贴着写.** 内容说完就停, 一段 280 字的 description 完全可以比一段 395 字的更好.
- **`github_about` 的上限性质不同.** description 的上限是我们自己定的风格预算; 这一条来自外部, GitHub 的 About box 约 350 字符就截断. 所以它没有下限, 短是优点不是缺点.

### 4.3 description, 写给学生的那段话

**黄金标准**: 你把课程链接丢给一个学生时, 这段话可以原样复制粘贴发给他. 所以它不是摘要, 不是目录, 是你对着一个具体的人说的话. 它是全套规范里唯一可以写长的 description, 允许多句, 该说的说完为止.

内容是两段式, 两件事都要有, 且要分得清:

1. **概述**: 这门课学的是什么. 让他知道这是关于什么的一门课, 一句人话就够.
2. **为什么值得学, 学完有什么收获.** 注意这是两件不同的事, 别只写一个. "为什么学" 是动机 (这东西在真实工作或学习里值什么, 不会它会怎样), "有什么收获" 是结果 (学完他手上多了什么能力). **只写动机不写收获是最常见的缺口.**

深浅档位如果要提, 自然融进第 2 点, 不单列成一项去凑.

**红线, 绝不罗列知识点.** 这是最常见也最要命的失败: 把各 Task 的知识点用几个词串成一串, 读起来像目录. 一旦写出 "涵盖 A, B, C, D" 这种句式就已经跑偏, 哪怕前面加了 "学完你能" 也一样. 主题的边界靠一句人话交代, 不靠枚举; 枚举是索引 Task 的活.

同理别写成 "本课介绍 XX" 这种第三人称课程简介口吻, 那不是能发给学生的话.

### 4.4 github_about, 写给老师的那句话

一个额外的短字段, 专门塞进 GitHub 仓库的 About box. 因为上面的 description 偏长, 进不了 About, 所以单列这个压缩版.

看它的是课程作者本人和其他老师, 在 About box 或课程索引里扫一眼, 望文生义就知道这个 repo 大概教什么. 所以**它只回答一件事: 这是教什么的.** 学完有什么收获在这里不重要, 不用写. 一句话, 越直白越好.

## 5. 正文, 三段

**段数就是三段.** 不是 "一般三段", 也没有第四段: 想说的第四件事要么并进第三段, 要么本来就不该出现在这份文件里.

三段各讲什么:

1. 这个要学的东西是什么, 为什么重要. 把它定位成常用工具, 业内标准, 或者解决某类问题的杀手锏.
2. 学完你能做什么, 到什么深度. 用真实工作里的价值来讲.
3. 其它值得单独说一段的, 比如教法, 边界, 怎么用, 从哪儿开始读.

**深浅档位是受控词汇, 不是形容词.** `basic`, `advanced`, `hardcore` 三个枚举值一律保留原词, 不要发挥成 "入门级", "进阶班", "这是一门高阶课程" 之类. 这一条不钉死, 每次写都会长出一种新说法, 同一个课程系列排进一个索引就会露馅.

**长度不设硬上限**, 理由有两条. 一是这份文件里混着大量保留原文的英文术语, 按字符数算不准, 定出来的数字对某些题材一定是错的. 二是它在发出去之前一定会被人从头读一遍, 不需要一个数字替人把关.

所以长度按内容厚薄走: 确实有东西可讲就多写两句, 没有就早点收. 一个软参考, 不是判据: 一段写到两百多字还没收住, 通常不是内容厚, 而是话没说利落, 该回头砍而不是继续加.

**只有两条是硬的**:

- **每段至少两句.** 一句话一段是没写完, 不是精炼.
- **一句话不要长到读者得回读一遍才断得对句.** 这条主要防的是把一串顿号列举硬攒成一个谁也读不动的长句.

第二条有一个例外, 而且是好例外: 冒号引出, 每一项都是同构短动词短语的排比句. 那种句子哪怕很长也读得动, 因为冒号已经替读者断好了句, 后面每一项的形状还都一样. 它和被禁的那种长句形态相反, 该留.

**结果先行, 企业视角.** 不要重复课程具体教的知识点, 不要罗列 1, 2, 3, 4 的学习目标. 整份文档 (含这三段) 是 pitch 不是目录.

## 6. 写作原则

- **术语保留英文.** 这是这份文件最容易翻车的地方: 中文只负责叙述, 术语, 产品名, 技术名词一律保留英文原文. 把 DataFrame 写成数据帧, 把 lazy evaluation 写成惰性求值, 读者反而认不出这门课在教什么, 这一行进了索引也失去检索价值.
- **链接**: 正文里指向 repo 内其他**文件**的相对路径链接用 `-cn` 版; 指向**目录**的链接不带语种后缀 (各语种的文件都在同一个目录下, 加后缀反而是死链).
- 遵循 `markdown-style` 与 `chinese-english-punctuation` 两个 Agent Skill.

## 7. 交付前自检

数得出来的:

- H1 与 repo 目录名逐字节一致, 包括 `-project` 后缀
- `description` 与 `github_about` 都用双引号包裹, 都是一行, 不含换行
- 两个长度都落在预算之内, 而且不是为了凑数硬撑出来的
- 正文正好三段, 每段至少两句

要读一遍才看得出来的:

- description 里 "为什么值得学" 和 "学完有什么收获" 两件事都在, 而且分得清
- description 没有出现 "涵盖 A, B, C, D" 这类枚举, 也没有 "本课介绍 XX" 这种第三人称口吻
- description 能原样复制粘贴发给一个学生
- github_about 只回答 "教什么", 没有掺进收获
- 档位写成 `basic`, `advanced`, `hardcore` 三个原词, 没有被译掉
- 术语保留了英文原文, 没有被强行译成中文
- 三段读下来是一段能念出来的 pitch, 不是一份目录
