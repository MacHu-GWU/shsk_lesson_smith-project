# Task TICKET 规范, 中文版

**适用范围**: 教学 Task 级的 `TICKET-cn.md`. 在 readup, upskill, showcase 里是 `examples/NN-title/TICKET-cn.md`; 在 evolve 里就在 Repo 根目录下. 四类同形, 所以这一份放在 `00-common` 下.

**不在适用范围内的**是 readup, upskill, showcase 三类 repo 根目录那份整门课的 TICKET. 它们各有专属 spec, 在本文件的三段式之上多一个 H2. 但受控词汇, H1, frontmatter, 链接这几条它们仍然继承本文件, **不要在那三份里另立一套**.

**配套骨架**: [task-ticket-cn-template.md](task-ticket-cn-template.md). 起草时把它整份复制过去填空, 里面没有任何注释, 复制完不用删任何东西.

**只管中文版**: 英文版另有一份 spec 和一份 template, 属于多语种模块, 现在还没做.

---

## 1. 它是什么

**这是任务卡片**, 最终会被程序放进 GitHub Project Issue 的 body.

主要给学生看, 也给导师或验收者看. 用途是告诉学生要做什么, 怎么做, 怎么检查和提交, 同时为验收者提供验收标准.

---

## 2. 与同目录 README 的关系

TICKET (怎么验收) 和同目录 README (教什么) 是**同一个 Task 的一对**, 一起写也一起改. 只改一边是统稿时返工最多的来源.

正文要逐节对齐:

| TICKET | 对齐 README 的 |
| :--- | :--- |
| 第 2 节 要做的事情 | 练习与操作步骤. 学生照着这一节做, 走的应该就是 README 里那条路 |
| 第 3 节 检查清单 | 学习目标. README 承诺 "学完你能 X", 这里就要有一条能当场验收 X 的 |

frontmatter 的两句也是一对, 分工不同: README 那句是**承诺** (学完能做到什么), TICKET 这句是**判据** (做出什么才算完).

---

## 3. 结构写死

三段式, **不许增删, 不许改名**. 三个 H2 按 markdown-style 从 1 连续编号, 之间用 markdown 分隔线隔开.

小节标题是受控词汇, 逐字写死:

```text
## 1. 目标
## 2. 要做的事情
## 3. 检查清单
**预计用时:**
```

根目录那份整门课的 TICKET 多一个第 4 节, 同样写死:

```text
## 4. 关键能力
```

**为什么钉死**: 不钉死, 每次写都会发挥出一种新说法 (任务目标, 完成清单, 步骤, 时间预估), 同一个课程系列排进一个看板就会露馅. 理由和 README-ORIGINAL 里档位那三个词一样.

---

## 4. H1

照通用规则, 见 [01-repo-layout.md](../01-repo-layout.md) 第 9 节, 那里是权威. 由 lint 卡死.

TICKET 的 H1 最容易踩的是**带连字符的术语** (`from-scratch mode` 这类词正文里合法, 进 H1 就报错), 以及**拿 repo 名当前缀**. 两条第 9 节都说了.

---

## 5. frontmatter, description

这个 Task 的**完成判据**: 一句话说清做出什么, 或能当场演示什么, 才算完成 (Definition of Done 压成一句). 它出现在看板与 Issue 列表里, 面向判断 "这活儿是啥, 达没达标" 的人.

它和同目录 README 那句是同一个 Task 的两张脸: README 句说学完能做到什么, 这句说做出什么才算完. **纯知识型 Task 就写成可当场检验的理解** (你能解释清楚 X).

**紧度按海拔走**: 这是 Task 级的 description, **一句话, 说完就停**. 别拿 README-ORIGINAL 那种用足预算的写法套过来.

中文版上限 400 字符, 没有下限. 形态约束 (一行, 双引号包裹, 哪些字符禁用) 见 [01-repo-layout.md](../01-repo-layout.md) 第 6 节, 那里是权威.

---

## 6. 链接约定

TICKET 正文最终会被程序放进 GitHub Issue, 所以对链接有讲究.

- **禁止指向 repo 内文件或目录的相对路径链接.** 相对路径在 GitHub Issue 里是死的, 点不动. 要指向 repo 里某个文件, 目录或 Task 时, **用文字提及** (直接说文件名或位置), 不写成链接.
- **允许绝对 URL**: 形如 `https://domain/href` 的绝对链接完全可以照常用.
- **不手写指向本教程或本 Issue 自身的 GitHub 链接**: 生成 Issue 时程序会确定性地拼出来.

这一条由 lint 卡死.

### 6.1 提到子 skill 时怎么写

upskill 与 showcase 的 TICKET 会提到 forge 产出的那几个子 skill. 写法只有一种, 全套统一:

- **正文里**: 反引号包住带斜杠的完整命令, 形如 `` `/upskill-quiz-cn` ``. 斜杠是学生真要敲的东西, 不能省; 反引号是为了让它一眼看出是一条命令而不是一个路径, 也挡住 markdown 把它当别的东西解析.
- **frontmatter 的 `description` 里**: 写**裸的** `/upskill-quiz-cn`, **不加反引号**. 这不是风格选择, 是硬约束: 反引号在 description 的禁用字符集里 (见 [01-repo-layout.md](../01-repo-layout.md) 第 6.2 节), 加了 lint 当场报错.

这一条不钉死就会长出三四种写法 (裸斜杠, 无斜杠裸名, 带反引号无斜杠), 而同一个课程系列排进一个看板就会露馅. 理由和受控词汇那一条一样.

---

## 7. 三节各写什么

**第 1 节 目标**: 1 到 3 段. 说清这个 Task 要完成什么, 以及为什么值得做. 不复述 README 的教学内容, 只交代这一趟的落点. 如果这个 Task 有一条学生最容易忽略的红线 (例如 "读完不算完, 得真交出一份东西"), **在这里点破**, 别留到检查清单才第一次出现.

**第 2 节 要做的事情**: 有序列表, 每条一个可执行动作, **动词开头**, 具体到学生知道手往哪儿放.

- "理解 X" 不是动作.
- "合上教程用自己的话讲一遍 X, 再回去对照哪里偏了" 才是.
- 顺序就是学生实际操作的顺序.
- 末尾单起一行给预计用时, 用受控词汇那一行的写法. 阅读量和动手量差得远时, 可以在括号里补一个只读不做的估计.

**第 3 节 检查清单**: markdown todo 列表, 每条一个 checkbox, 形如粗体标签加冒号加一句完成标准.

```text
- [ ] **标签**: 完成标准的简述.
```

- **每条都要能被第三方当场判定真假.** 理解型的写成 "你能说清 X" 或 "你能举出 X", 产出型的写成 "X 已经存在于哪里, 长什么样".
- 常见区间是 5 到 9 条. 少于 5 条通常是 README 的学习目标没被逐条接住, 多于 9 条通常是把 "要做的事情" 又抄了一遍.

---

## 8. 交付前自检

数得出来的:

- 正好三个 H2 (根 TICKET 是四个), 编号从 1 连续, 之间有分隔线
- 每个 H2 的文字逐字等于受控词汇表里那一行
- H1 里没有连字符, 破折号, 引号, 方括号, emoji, 也没有 repo 名前缀
- description 一行, 双引号包裹, 400 字符以内
- 第 2 节末尾有预计用时那一行
- 全文没有任何指向 repo 内文件或目录的相对路径链接

要读一遍才看得出来的:

- 每条 "要做的事情" 都是动词开头的可执行动作, 顺序就是实际操作顺序
- 每条检查项都能被第三方当场判定真假, 没有 "理解了 X" 这种判不了的
- 检查清单逐条对得上 README 的学习目标, 要做的事情对得上 README 的操作步骤
- description 写的是判据 (做出什么才算完), 不是承诺 (学完能做到什么)
