# 统稿规范

各个 Task 是分头写出来的, 合起来未必是一条线. 这一步通读全系列, 把它变成一条线.

**适用范围**: readup, upskill, showcase 三类. evolve 没有 `examples/` 这一层, 一个 branch 一个 Task 各自独立, 没有 "系列" 可统, 不适用.

**位置**: `examples/` 下全部 Task 写完之后, 包括开头的索引 Task 和结尾的收尾 Task. 再往后的顺序是: readup 走**根目录文档, 出厂**; upskill 与 showcase 中间多一步锻造, 走**forge, 根目录文档, 出厂**. **forge 在根目录文档之前**, 因为根 README 要指名道姓提到 forge 产出的那几个子 skill.

**一次只统一个语种.** 中文统中文的, 英文统英文的, 不要跨语种对照着改. 当前只有中文.

**为什么单独一步**: 后面几步都拿 examples 当稳定素材 (根 TICKET 要从它们萃取关键能力, 根 README 要梳理怎么读). 素材本身还在漂的时候做这些, 全是白做. **这一步是主线成文的判据.**

**为什么建议开新 session**: 它要通读全部 Task, 而写作阶段留下的上下文 (讨论过的取舍, 改过又改回去的段落) 只会挤占注意力. 拿一个干净的上下文读成品, 看到的东西不一样.

**但这个新 session 是从补两头那一步就开始的, 不是到统稿才开.** 补两头本来就要通读全系列, 统稿要的是同一次通读; 三份工作流都把这两步放进同一个 session, 照那个走.

---

## 1. 先通读, 再动手

按编号顺序把 `examples/*/README-cn.md` 与 `examples/*/TICKET-cn.md` 从头读到尾.

**一次读完再动手改, 不要边读边改.** 第 3 篇的问题往往要读到第 8 篇才认得出来: 一个术语第一次出现时看不出毛病, 要等它第二次以另一个名字冒出来, 你才知道第一次那个是错的.

找的东西分两类: **纠错**和**改稿建议**. 两类的处置方式不同, 见第 4 节.

---

## 2. 纠错: 找不一致

这一类是客观的对错, 找到就该改.

**术语与命名不一致.** 同一个概念在不同篇里叫了不同的名字, 或者同一个名字在不同篇里指了不同的东西. 这是最常见也最伤的一类, 因为学生会以为那是两个东西.

**表达方式不统一.** 同一种东西每篇的写法不一样: 命令有的带 `$` 有的不带, 路径有的绝对有的相对, 同一类提示有的用引用块有的用粗体.

**深浅与风格漂移.** 前几篇是试水时写的, 后几篇是熟练之后写的, 中间往往有一道坎: 篇幅忽长忽短, 假设的前置知识忽深忽浅, 讲解的颗粒度对不上. **以定稿的风格为准往回统一, 不是以第 1 篇为准.**

**前后矛盾.** 同一件事在两篇里给了不同的说法, 或者前面说 "后面会讲" 而后面没讲, 或者后面用到了前面没交代过的东西.

**承上启下断掉.** 每篇开头该接住上一篇留下的东西, 结尾该给下一篇铺路. 分头写的时候这些接口最容易缺失, 读起来就是一堆独立文章而不是一门课.

**README 与 TICKET 脱节.** 每个 Task 的 TICKET 的 "要做的事情" 要呼应它 README 的练习与操作步骤, "检查清单" 要呼应学习目标. 改了 README 而 TICKET 没跟上, 是写作阶段的典型欠账.

---

## 3. 改稿建议: 看整体形状

这一类没有绝对的对错, 是拿整体看局部才看得出来的问题. **只提建议, 由创作者定夺.**

**头重脚轻.** 各篇篇幅的分布合不合理. 常见的是前两篇写得极细 (那时还有劲), 后面越写越薄; 也有反过来的, 开头草草带过, 真正的重头戏堆在最后一篇里.

**该拆的没拆.** 一篇里塞了两三个不相干的知识点, 学生一次咽不下去.

**该并的没并.** 相邻两篇讲的是同一件事的两半, 分开之后每篇都撑不起一个 Task.

**规定动作齐不齐.** 对着这个 repo type 的 repo layout 核一遍: 开头有没有索引 Task, 结尾有没有收尾 Task, 中间位置固定的特殊 Task 在不在该在的位置. 少一个就在这里提出来.

**规划里说要覆盖的漏没漏.** 拿 `examples/_lm-example-plan.md` 和成品对一遍.

---

## 4. 改法

**先列出来给创作者过目, 再动手.** 把找到的按上面两类分组列出来, 每条给出在哪篇, 什么问题, 打算怎么改.

- **纠错**那一类要点明打算统一成哪个, 因为那是创作者的口味.
- **建议**那一类明确标成建议, 不要写得像已经定了. 拆篇并篇是伤筋动骨的改动, 创作者可能有你不知道的理由.

他点头之后再改.

**成批改, 不要一篇篇过.** 术语统一这类跨篇的改动, 一次改完全部出现的位置, 别改一篇算一篇.

**改完复读被改动的段落.** 尤其是术语替换, 换完之后句子常常读起来别扭, 因为原来那个词是句子长出来的骨架.

---

## 5. 什么时候算过

三条都满足才进下一步:

- 第 2 节那几类都过了一遍, 找到的都改完.
- 第 3 节的建议都提给创作者了, 他逐条明确说了改还是不改.
- 从头到尾读下来是一条线, 不是一堆独立文章.

还有第四条, 不能省:

- **创作者本人点头说主线可以了.**

这一步的判据里有大量口味成分, 不是 AI 能单方面宣布通过的.
