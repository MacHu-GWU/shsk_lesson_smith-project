# 作品 README 指南, 信息块菜单

**适用范围**: `showcase-publish-cn` skill 陪学生写发布后根目录 `README.md` 时读的参考. forge 把本文件原样拷进生成 skill 的 `ref/` 下, 学生 repo 里没有 lesson-smith, 所以它必须自带.

**它不是模板.** 这里没有章节骨架, 没有固定顺序, 没有字数要求. 它只回答一个问题: 一份公开项目的 README 可以放哪些**信息块**, 用什么手段把它们呈现得好看. 每个信息块都是**推荐, 不是必须**. 两个学生做出来的 README 长得不一样, 是这份指南的目标, 不是偏差.

---

## 1. 定位

这是学生**自己一个公开项目的 README**. 读它的人是路过的陌生人: 招聘方, 同行, 想找轮子的开发者. 他们扫一眼, 十几秒内决定要不要往下读.

所以好 README 的标准只有一条: **一个陌生人扫完前几屏, 知道这是什么, 为什么值得看, 这东西是真的.** 至于用什么块, 怎么排, 放多长, 由这个项目自己的分量决定.

它不是教程, 不是课程总结, 也不是给导师交的作业. 它要读起来像学生自己做了一个项目, 然后向别人介绍它.

---

## 2. 信息块菜单

下面是常见的信息块. **有真东西可写就写, 没有就整块跳过, 不要为了凑齐而编.** 顺序自由, 可以合并, 可以拆开, 也可以加菜单里没有的块.

| 信息块 | 回答什么 | 适合的呈现 |
| :--- | :--- | :--- |
| 徽章 | 语言, 版本, 许可证, CI 状态这类一眼能确认的事实 | 顶部一排 shields.io 徽章 |
| 一段话简介 | 这是什么, 谁会在乎 | 2 到 4 句话, 可以配一句 `> [!NOTE]` 强调 |
| 解决的问题 | 没有它时痛在哪 | 一段话, 或 before 与 after 对照表 |
| 演示与效果 | 跑起来长什么样 | 截图, 动图, 终端输出的代码块 |
| 架构与数据流 | 由哪几块组成, 数据怎么走 | mermaid 图, 图下面一段话点出关键路径 |
| 快速开始 | 从 clone 到跑出结果的最短路径 | 一个 `bash` 代码块, 只放真的能跑的命令 |
| 技术选型与取舍 | 为什么选这个不选那个 | 表格: 选择, 备选, 理由 |
| 技术细节与创新点 | 有没有值得单拎出来讲的做法 | 一小段加代码片段或时序图, 没有真创新就跳过 |
| 结果 | 做出来的效果, 数字 | 指标表, 对比表, 图 |
| 项目结构 | 目录怎么组织 | 目录树代码块, 只列关键部分 |
| 踩过的坑与收获 | 最难的一段, 怎么过的, 学到了什么 | 一两个具体事件, 配 `> [!TIP]` 或 `> [!WARNING]` |
| 局限与下一步 | 诚实地说还缺什么 | 短列表 |
| 许可证, 联系方式, 致谢 | 别人怎么用, 怎么找到你 | 一两行 |

有几条选块的经验, 供参考, 不强制:

- 一份 README 通常只有五六个块真正撑得起来, 多了反而稀释重点.
- 架构图, 结果表这类**可视化**块比同样信息量的大段文字更好读, 有条件优先用.
- 小项目可以只有简介, 快速开始和一张架构图.

## 3. 呈现手段

README 是一个用来看的页面. 能用可视化表达的地方, 尽量别写成大段文字.

**表格**. 适合对照类信息: 选型取舍, before 与 after, 指标, 配置项. 一格一个事实, 别塞长句.

**mermaid 图**. GitHub 原生渲染. 按要讲的东西选类型:

| 想讲什么 | 用什么图 |
| :--- | :--- |
| 模块之间怎么连, 数据怎么流 | `flowchart` |
| 几个参与方按时间顺序怎么交互 | `sequenceDiagram` |
| 数据表和关系 | `erDiagram` |
| 一个东西有哪些状态怎么转 | `stateDiagram-v2` |
| 项目怎么随时间推进 | `timeline` 或 `gantt` |

画图的规矩只有几条: 节点名用**真实的模块, 文件, 服务名**, 必须对着实际代码画, 不凭想象补; 一张图控制在十五个节点左右, 再多就拆成两张; 语法要写对, 写完自己读一遍.

**提示块**. GitHub 支持五种 alert, 写法是引用块的第一行放类型标记:

```markdown
> [!NOTE]
> 读者容易忽略但值得知道的一条信息.
```

| 类型 | 用来放什么 |
| :--- | :--- |
| `[!NOTE]` | 补充信息, 背景 |
| `[!TIP]` | 经验, 更好的做法 |
| `[!IMPORTANT]` | 不做就跑不起来的关键点 |
| `[!WARNING]` | 容易出问题的地方 |
| `[!CAUTION]` | 可能造成数据丢失或不可逆后果的操作 |

GitHub 只认这五个标记, `[!INFO]` 这种写法会被当成普通引用块, 标记文字会原样露出来. 提示块要克制使用, 一页里出现三四处就够了.

**徽章**. 用 shields.io. 每个徽章必须**对应真实存在的东西**: 语言与版本可以读 `pyproject.toml` 或 `package.json`, 许可证读 `LICENSE`, CI 徽章只有 `.github/workflows/` 下确有那个 workflow 才放, 覆盖率, PyPI 这类只有真的接入了才放. 指向一个不存在的 workflow 的徽章会显示成破图, 比没有更糟.

**图片与截图**. 图片文件必须已经在 repo 里 (例如 `docs/images/`), README 里的路径必须解析得到. skill 不能凭空生成截图, 学生有就用, 没有就问他要或者跳过, 不许引用不存在的文件.

**折叠块**. 长的配置, 完整输出, 次要的说明可以放进 `<details>`, 让主线保持干净.

## 4. 语气

语气只管口吻和侧重, **不决定用哪些块, 也不决定顺序**. 起草前给学生一道选择题, 让他选一种, 也可以选混合, 或者自己描述.

| 语气 | 读起来像 | 侧重 |
| :--- | :--- | :--- |
| 实用说明书 | 一份清楚的产品手册 | 它做什么, 怎么用, 别的少说 |
| 建造日志 | 做这个东西的人在讲经过 | 做了哪些决定, 绕了哪些弯路 |
| 问题先行 | 一个小型案例研究 | 先讲痛点, 再讲解法, 再讲结果 |
| 公开复盘 | 做完之后诚实地回头看 | 意外, 失误, 收获 |
| 精简技术向 | 给同行扫读的技术摘要 | 栈, 取舍, 指标, 少铺垫 |

人称同样是学生的选择: 第一人称最自然, 因为项目是他做的; 他偏好中性叙述也可以.

## 5. 几条硬约束

这份指南几乎不限制风格. 下面几条不是风格问题, 是为了不出事, 所以是硬的.

**真实, 不编造.** 每一个事实, 数字, 命令, 特性, 都来自学生的话或者 repo 里读到的文件. 某个块缺事实, 就问学生要, 要不到就整块跳过, 不许替他想.

**不露教学来源.** 正文里不许出现下面这些, 中英都算:

- 词汇: 教程, 本课, 这门课, 我们学过, 作为学生, 练习, 课程, tutorial, course, lesson, curriculum, syllabus, exercise, student, quiz.
- 名字: `showcase-`, `TICKET`, `README-ORIGINAL`, `lesson-smith`, `NN-prove-i-get-it`, `NN-how-i-build-this`.
- 链接: 任何指向已被发布流程删掉的路径的链接.
- 文件头: 第一行不能是 `---`. lesson-smith 的 frontmatter 放在 README 顶部, GitHub 会把它渲染成一张表, 一眼就露馅.

**链接和图片对着发布后的树写.** 写 README 时教学痕迹还没删, 所以每个相对链接和图片路径, 都要对照发布前算好的 "发布后的树" 来写, 只链到删完之后还在的东西, 而且用去掉语种后缀之后的文件名.

**每个论断有只属于这个项目的细节.** 一个真实的报错信息, 一个具体数字, 一个改主意的决定, 一个奇怪的边界情况. 没有这种细节的句子, 换个项目也成立, 就是套话.

**停用套话.** 下面这些一律不用, 换成具体的说法:

- 英文: seamless, robust, leverage, cutting-edge, state-of-the-art, comprehensive, powerful, blazing fast, easy-to-use, in today's fast-paced world.
- 中文: 赋能, 一站式, 打造, 全方位, 极致, 无缝.

**学生的措辞优先.** 他改了哪个词, 就以他的为准. 起草时尽量保留他原话里那些有个性的说法.

## 6. 选英文时怎么写

学生完全可以用中文回答问题, skill 直接写英文. 这是**改写, 不是逐句翻译**: 先理解他要说什么, 再用英文母语者会这样说的方式写出来.

- 短句, 主动语态, 具体的动词.
- 避免中文句式的直译: 长串定语堆在名词前, "通过 X 来实现 Y" 一路译成 "through X to realize Y", 每句都以 "It is" 或 "We can" 开头.
- 术语, 命令, 文件名, 专有名词保持原样.
- 写完读一遍, 凡是读起来像翻译的句子, 重写.

选中文或其他语种时这一节不适用.

---

## 7. 交给学生之前的自检

- 每个块都有真事实撑着, 没有为了凑数硬写的块
- 没有不存在的图片, 徽章, 命令, 链接
- 没有教学词汇, 没有指向已删路径的链接, 第一行不是 `---`
- 至少一处可视化 (表格或 mermaid), 而且 mermaid 里的名字都能在代码里找到
- 抽两三句话看: 换一个项目还成立的, 重写
- 学生读过, 并且他认为这是他的 README
