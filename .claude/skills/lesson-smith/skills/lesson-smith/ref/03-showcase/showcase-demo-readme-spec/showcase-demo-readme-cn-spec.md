# Showcase demo Task 的 README 规范, 中文版

**适用范围**: 仅 showcase 类型 repo 里 demo 那个 Task 的 `README-cn.md`, 目录固定命名 `examples/ZZ-how-i-build-this`.

它住在 `examples/` 下, 但**不走** [00-common/03-task-readme-spec](../../00-common/03-task-readme-spec/task-readme-cn-spec.md) 的教学正文结构, 而走下面这套讲故事结构. **frontmatter, H1 与链接三条仍以通用规范为准**, 不要在这里另立一套.

**配套骨架**: [showcase-demo-readme-cn-template.md](showcase-demo-readme-cn-template.md).

**只管中文版**: 英文版另有一套, 属于多语种模块, 现在还没做.

---

## 1. 它是什么

**讲故事底稿**, 即 "这个 repo 可以怎么讲" 的真身. 它是 `examples/` 的**最后一个 Task**.

别人问你 "你怎么做 XX 这件事" 时, 你就用这个 repo 讲: 当时怎么学的, 遇到什么问题, 怎么解决的. 因为学生真的掌握了底层能力, **抹去教学痕迹后把它当自己的作品来讲是完全正当的**.

`docs/showcase/04-showcase-demo.md` 只是一层指过来的薄壳, `/showcase-demo` 拿它来陪学生排练.

视角是**学生第一人称** (我是怎么做出这个的). 配套的 TICKET 另有规范, 见 [showcase-demo-ticket-spec](../showcase-demo-ticket-spec/showcase-demo-ticket-cn-spec.md).

---

## 2. 它和 publish 的关系

**demo 是在 publish 之前读的.** 学生先靠这份底稿把故事排练好; 之后跑 `/showcase-publish` 时, `ZZ-how-i-build-this` 这个 Task, `docs/showcase/04-showcase-demo.md` 以及 `showcase-demo` skill 都会作为教学痕迹被删掉.

也就是说**底稿服务于排练, 排练完它的使命就结束了**. 真正带走的是学生脑子里那套能讲的故事和背后的能力.

写的时候就按这个前提写: 它是排练材料, 不是要长期留在 repo 里的门面.

---

## 3. 默认故事主线

**这是本 spec 的核心.** 90% 的情况下, 创作者没有特殊说明时, showcase repo 的故事主线就是下面这七幕.

它讲的是 "我如何用 AI 快速把一个技能学会并投入实战" 这套方法论本身, 既是作品叙事, 又顺带证明了 AI 协作能力.

| 幕 | 内容 |
| :--- | :--- |
| 1 | 我在学习或工作中发现某个技能在某个领域很重要, 值得投资把它学会 |
| 2 | 我先让 AI 调研这个技能有哪些权威资料 |
| 3 | 把这些资料蒸馏成一个囊括该技能的超级专家 AI agent skill |
| 4 | 告诉 AI 我的情况, 让这个超级专家设计一个我一周能执行完的课程大纲 (落成 `examples/01` 索引 Task) |
| 5 | 按大纲的每一个点, 让 AI 产出一个我能阅读又能上手练习的例子 (落成 `examples/02` 往后的各个教学 Task) |
| 6 | 在 AI 的持续陪伴下把这门课学完 |
| 7 | 把学会的技能投入到真实的学习和工作里解决实际问题 |

创作者写这份底稿时, 就是**把这七幕用自己这个具体 repo 的实际内容填实** (某技能, 某领域, 具体调研了什么, 大纲长什么样, 例子是哪些).

如果这个 repo 的真实经历确实偏离默认主线, 可以改写某几幕, 但**要保留这条骨架**: 发现价值, 蒸馏专家, 设计大纲, 逐例练习, 投入实战.

---

## 4. 四个 H2 各写什么

H2 按 markdown-style 从 1 连续编号, 相邻小节之间用分隔线隔开.

**第 1 节 一句话故事.** 2 到 3 句的电梯版, 别人只给你一句话时间时怎么讲.

**第 2 节 默认故事主线.** 上面那七幕. 每一幕一个 H3 (第 N 幕加一个短标题), 幕下两块:

- 加粗的 "怎么讲" 后跟一个 blockquote, 承载第一人称的讲法.
- 加粗的 "对应产物" 后跟一行, 用 markdown 链接指到 repo 里支撑这一幕的产物. 定位用 header 或关键字, **不用 line no**.

**第 3 节 常见追问与怎么接.** 列几个听众 (面试官) 可能追问的问题, 每个给一个怎么接的思路. 每个追问一个加粗小标题, 下面一个 blockquote 给要点.

- 这些是关于**这段经历和方法**的元问题: 为什么选这个技能, AI 生成的东西你真懂吗, 遇到最大的坑是什么, 这套方法能不能复用到别的技能.
- **不考具体技术知识, 那是 quiz 那个 Task 的活.**

**第 4 节 按听众裁剪 (可选).** 一小段, 说清面对不同听众 (对口岗位面试官, 不对口岗位面试官, 同行, 非技术) 时该突出哪几幕, 或者诚实建议别讲这个 repo.

---

## 5. 写作原则

- **第一人称, 口语化.** 这是能直接说出口的话, 不是书面报告.
- 溯源一律 markdown 链接加 header 或关键字, 不用 line no.
- **诚实, 不夸大.** AI 帮了多少就说多少, 半成品就说半成品. 讲清 "我真的掌握了底层能力" 靠的是能答追问, 不是嘴上说.

---

## 6. 交付前自检

- 四个 H2, 编号连续, 之间有分隔线; 第 2 节下七个 H3
- 每一幕都有 "怎么讲" 和 "对应产物" 两块, 产物链接活的
- 七幕都用这个 repo 的实际内容填实了, 没有留下模板占位符
- 第 3 节全是元问题, 没有混进技术知识题
- 通篇第一人称, 读出来像人话
- frontmatter 的 description 在, 值用双引号包着 (见 [00-common/01-repo-layout.md](../../00-common/01-repo-layout.md) 第 6 节)
