# Vercel 基础课自测题

> 本文档是对整门课学到的东西的一次验证, 看你是否不仅知其然, 更知其所以然. 三十道题大多是你以后真会遇到的场景: 先自己想一遍该怎么做, 再对照参考回答与深入解读. 每道题末尾都给了溯源, 想不通就回去把那一节重读一遍.

## 1. Vercel 到底解决了什么问题

**问题**

> 下面这些事情, 在没有 Vercel 这类平台的年代都得你自己处理: 租一台一直开着的服务器; 配防火墙决定放行哪些端口; 买域名并配 DNS 解析; 申请 HTTPS 证书, 还要记得三个月后续期; 程序崩了要能自动重启; 日志要自己搭一套来收集和搜索; 用户变多要加机器并配负载均衡; 海外访问慢要配 CDN; 每次改完代码还要手工走一遍上传, 重启, 验证.
>
> 从里面挑四到五件, 说说 Vercel 分别是怎么把它变成你不用管的.

**考察点**

> 不考你能不能背出这张清单, 清单已经给你了. 考的是你能不能把每一件事对应到 Vercel 的某个具体行为上, 也就是你到底理解不理解这个平台在替你干什么.

**参考回答**

> **服务器和自动重启**: 你根本不需要有 "一台机器" 的概念. 代码交上去就在跑, 挂了平台自己处理, 你看不到也不用管.
>
> **域名和 HTTPS**: 部署完成就直接给你一个可访问的网址, 证书自动配好也自动续期, 你从头到尾没接触过证书这个东西.
>
> **日志**: 开箱即用, 一行配置都不用写. 部署过程和运行过程的日志分别在 Build Log 和 Runtime Log 里, 直接能看能搜能筛.
>
> **CDN 和扩容**: 全球分发是默认行为, 不需要你选节点, 也不需要在用户变多时加机器.
>
> **每次发布的手工流程**: 被 GitHub 联动取代了. 你往仓库提交, Vercel 自动检测到并重新构建部署, 你一个按钮都不用点.

**深入解读**

> 答这道题的时候要抓住一个判断: **复杂度不会消失, 只会转移**. 你今天不用配防火墙, 不是因为防火墙不重要了, 而是 Vercel 替你配了.
>
> 这个认知能防止一种危险的错觉, 就是以为这些底层的东西已经不存在了. 它们还在, 只是暂时不归你管. 等到有一天你的需求超出平台的默认假设, 它们会立刻回到你面前.
>
> 溯源见 [01-why-vercel 的 "5. 十年前, 让一个网站上线要过多少关"](../01-why-vercel/README-cn.md), 以及 [02-sign-up-vercel 的 "5. Vercel 到底替你做了什么"](../02-sign-up-vercel/README-cn.md).

## 2. 把 Vercel 的职责讲给外行听

**问题**

> 一个完全不懂技术的朋友问你: Vercel 是个什么东西? 先用一句话概括, 再展开说它具体做哪几件事.

**考察点**

> 考你能不能准确划出这个平台的职责范围. 说得太窄会漏掉它的核心价值, 说得太宽会让人以为它连代码都帮你写.

**参考回答**

> 一句话说, Vercel 是一个帮你把代码变成网站的平台.
>
> 具体做四件事: 把代码构建成能运行的网站; 分配一个公开的网址; 让全球的访问者都能打开这个网址; 在运行过程中持续记录日志和状态, 出了问题能查.

**深入解读**

> 注意这四件事里没有 "帮你写代码". Vercel 接手的是代码写完**之后的那一段**.
>
> 这个边界不是学术区分, 它决定了你遇到问题时该往哪儿看. 页面上数字算错了, 那是代码逻辑的事; 网站压根打不开, 才是部署这一层的事. 分不清的人会在错误的地方查半天.
>
> 溯源见 [02-sign-up-vercel 的 "5. Vercel 到底替你做了什么"](../02-sign-up-vercel/README-cn.md).

## 3. 你想知道自己离上限还有多远

**问题**

> 你在 Hobby 计划上跑着几个项目, 想确认一下用量. 你会去哪儿看? 如果哪天真超了, 会发生什么, 会收到账单吗?

**考察点**

> 考两件事: 你知不知道用量是可以实时查的, 以及你对超额后果的判断准不准. 后者直接决定你敢不敢放心用.

**参考回答**

> 用量在 Vercel Dashboard 的用量页面能实时看到. 文档上的额度是静态数字, 用量页面是自己的真实位置, 两个都要会看.
>
> 超额不会收到账单. Hobby 是免费层, 没有账单周期. 超了之后 Vercel 的做法是把那个功能暂停掉, 等满三十天再恢复, 而不是让你继续跑然后计费. 最坏的结果是用不了, 不是欠钱.
>
> 额度大致是每月一百万次请求, 一百万次函数调用, 两百个项目, 每天一百次部署. 但这些数字会变, 真要确认应该去看官方的定价页面和 Hobby 计划文档.

**深入解读**

> 这道题不要求你背准数字, 要求你记住两个结构性的事实.
>
> 一是**项目数和每天部署次数是有上限的**, 不是无限. 很多人凭印象觉得免费计划在这些地方应该没限制, 实际上项目上限两百个, 每天部署上限一百次. 学习阶段远远够用, 但知道有天花板和以为没有, 是两种状态.
>
> 二是**超额之后是暂停, 不是计费**. 按量计费的平台超了额度会继续服务然后照单收费, 所以才有那些巨额账单的故事; Hobby 是硬性暂停, 天花板是确定的. 你以后评估任何云服务, 都该先问一句它超额之后是暂停还是继续计费, 这一个问题就能筛掉大部分财务风险.
>
> 溯源见 [02-sign-up-vercel 的 "6. 免费计划够不够用, 会不会被扣钱"](../02-sign-up-vercel/README-cn.md).

## 4. 你的个人项目开始赚钱了

**问题**

> 你用 Hobby 计划部署的一个小工具意外地有人愿意付费了, 你打算正经做起来. 这时候有件事必须处理, 是什么?

**考察点**

> 考你会不会在用一个免费服务之前把条款看一眼. 这类问题不会立刻报错, 所以只有事先知道的人才会主动处理.

**参考回答**

> 必须升级计划. 按官方的 fair use 条款, Hobby 计划限定为**非商业的个人用途**. 拿它学习, 做作品集, 做个人项目都没问题, 一旦变成商业用途就不合规了, 该升级到 Pro.

**深入解读**

> 这一条的麻烦之处在于它不给你任何即时反馈. 你拿 Hobby 跑一个商业项目, 短期内多半什么事都不会发生, 直到某天平台注意到并采取措施. 属于典型的 "错了要很久才发现" 的那类问题.
>
> 这类问题的正确应对方式是在动手之前就知道它存在, 因为事后补救的成本远高于事前了解.
>
> 溯源见 [02-sign-up-vercel 的 "6. 免费计划够不够用, 会不会被扣钱"](../02-sign-up-vercel/README-cn.md) 的最后部分.

## 5. 朋友嫌注册麻烦

**问题**

> 你朋友要注册 Vercel, 看到有 "用 GitHub 继续" 的按钮, 说这样最快, 省得再记一个密码. 你会劝他吗? 怎么劝?

**考察点**

> 考账户独立性这个职业习惯. 这类判断短期毫无感觉, 长期影响很大, 能讲清楚说明你有系统性的风险意识.

**参考回答**

> 会劝, 建议他用独立邮箱注册.
>
> 理由是: 用 GitHub 账号登录, Vercel 账号的登录凭据就寄生在 GitHub 上了. 哪天 GitHub 账号出状况, 比如被风控误判成机器人, 或者忘了密码而恢复流程卡住, 他的 Vercel 账号也跟着进不去, 上面部署的项目全都会受影响.
>
> 用独立邮箱注册, Vercel 账号跟着他自己的邮箱走, 别的平台出什么事都牵连不到.
>
> 顺带一提, 也别用公司邮箱注册个人账号, 换工作时公司邮箱会被停用, 挂在上面的东西都要不回来.

**深入解读**

> 有个检验方法很好用: 问自己一句, 如果这个第三方账号明天没了, 我还能登进这个服务吗? 能, 说明它只是个数据源; 不能, 说明它是你的门. 门要自己掌握.
>
> 一个从业者的职业生涯里会注册几百个第三方服务. 如果它们层层套娃地互相依赖, 有一天某一环断了, 你会花很长时间才理清楚到底哪儿断了.
>
> 这道题很容易引出一个追问: 那部署的时候不是还要授权 Vercel 访问 GitHub 吗? 那是另一回事, 见第 9 题.
>
> 溯源见 [02-sign-up-vercel 的 "7. 为什么用独立邮箱注册而不是 GitHub 登录"](../02-sign-up-vercel/README-cn.md).

## 6. 你点下了 Deploy

**问题**

> 你在 Vercel 模板库里选中一个 Template, 点了 Deploy. 在你等待的这一两分钟里, 系统实际做了哪两件事? 这两件事的顺序为什么重要?

**考察点**

> 考你能不能把一个看起来像魔法的按钮拆解成具体动作. 这条链路是后面好几道题的共同地基, 拆不开的话讲环境和讲排错都会悬空.

**参考回答**

> 做了两件事, 不是一件.
>
> 第一件发生在 GitHub 那边: Vercel 在我的 GitHub 账户下新建一个仓库, 把 Template 的代码原样复制进去. 从这一刻起那份代码就是我的了, 和原作者的仓库再无关系.
>
> 第二件发生在 Vercel 这边: Vercel 把这个刚建好的仓库登记成一个项目, 读取代码, 构建, 部署上线.
>
> 顺序重要是因为链路方向是**代码先进 GitHub, 再从 GitHub 进 Vercel**. 理解了这个方向就理解了自动部署: Vercel 是盯着我的 GitHub 仓库看的, 所以以后每次往那个仓库提交改动, 它都会察觉并自动重新构建部署, 我不需要再点任何按钮.

**深入解读**

> 顺便说清 Template 本身: 它本质上就是一个公开的 GitHub 代码仓库, 别人已经写好并验证过能跑的完整项目. 没有任何 Vercel 专有的魔法在里面.
>
> 这条链路是第 7 题和第 8 题的共同前提. 你会发现很多看似不相干的问题, 最后都能顺着这条链路解释清楚.
>
> 溯源见 [03-deploy-your-first-app 的 "5. Template 到底是什么"](../03-deploy-your-first-app/README-cn.md).

## 7. 你想改网站上的一句话

**问题**

> 你的网站上有一句文案写错了, 想改掉. 你会去哪儿改? 为什么不是在 Vercel 的界面上找个地方改?

**考察点**

> 考你有没有建立正确的方向感. 搞反了的人会在 Vercel 上到处找编辑入口, 找不到还以为是自己权限不够.

**参考回答**

> 去 GitHub 仓库里改代码.
>
> 因为 **GitHub 仓库是唯一真相来源**, 网站长什么样完全取决于那个仓库里的代码是什么样. Vercel 的角色是盯着这个仓库, 一旦发现新提交就重新构建部署. 它是个执行者, 不是内容的存放处.
>
> 所以正确动作是在 GitHub 上改代码并提交, 剩下的 Vercel 会自动完成.

**深入解读**

> 这个方向感能帮你排查一整类问题, 因为它把系统拆成了两段: GitHub 那段负责 "内容是什么", Vercel 这段负责 "把内容变成网站". 遇到问题先判断是哪一段的事, 范围立刻缩小一半.
>
> 比如网站内容不对, 先去 GitHub 看看代码到底是什么样, 而不是在 Vercel 上翻设置. 反过来, 如果 GitHub 上代码明明是对的, 那问题就在 Vercel 这一段, 该去看构建日志了.
>
> 溯源见 [03-deploy-your-first-app 的 "5. Template 到底是什么"](../03-deploy-your-first-app/README-cn.md) 的后半部分.

## 8. 你提交了代码, 但 Vercel 毫无反应

**问题**

> 你在 GitHub 上改完代码提交了, 但等了几分钟, Vercel 的 Deployments 页面一条新记录都没有. 你会从哪儿开始查?

**考察点**

> 考你能不能用第 6 题那条链路来定位问题. 知道链路的人会直奔某一环, 不知道的人只能到处乱翻设置.

**参考回答**

> 顺着链路想: 正常流程是我提交到 GitHub, GitHub 通知 Vercel, Vercel 开始构建. 现在没有新的部署记录, 说明卡在**通知这一环**, 也就是 GitHub 和 Vercel 之间的连接上.
>
> 所以查的方向是这两边的连接: Vercel 项目还连着这个仓库吗, GitHub 那边的授权还在不在, 有没有被撤销过.
>
> 另外先排除一个低级情况: 确认自己提交到的确实是这个项目对应的那个仓库, 而不是提交错了地方.

**深入解读**

> 这道题的价值在于示范一种排查方式: **先在脑子里画出正常链路, 再看断在哪一环**. 这比漫无目的地翻设置高效得多, 而且适用于任何系统, 不只是 Vercel.
>
> 注意这里并不需要你知道具体去点哪个设置项. 判断出 "问题在连接这一环", 就已经足够让你搜到答案或者问对 AI 了. 这正是这门课反复强调的: 定位比解决更重要.
>
> 溯源见 [03-deploy-your-first-app 的 "5. Template 到底是什么"](../03-deploy-your-first-app/README-cn.md), 以及 [04-deployment-environment-and-git-branch 的 "8. Branch 决定贴哪张标签"](../04-deployment-environment-and-git-branch/README-cn.md).

## 9. 授权页面弹出来了

**问题**

> 第一次部署的时候, 中途跳出一个 GitHub 页面, 问你要不要允许 Vercel 访问你的 GitHub 账户. 这和第 5 题说的 "别用 GitHub 登录" 矛盾吗?

**考察点**

> 全套题里最容易被绕进去的一道. 考你能不能分清认证和授权这两种不同性质的关系, 而不是笼统地觉得 "反正都是把两个账号连起来".

**参考回答**

> 不矛盾, 这是两种完全不同的关系.
>
> | 维度 | 用 GitHub 登录 Vercel | 授权 Vercel 访问 GitHub |
> | :--- | :--- | :--- |
> | GitHub 扮演什么 | 我进入 Vercel 的**大门** | 一个**数据源** |
> | 我的登录凭据在哪 | 寄生在 GitHub 那边 | 还是我自己的邮箱和密码 |
> | 这条关系断了会怎样 | 我进不去 Vercel | 少一根数据管道, 账号本身没事 |
> | 能不能随时撤销 | 撤了就登不进去了 | 能, 去设置里撤销即可 |
>
> 门锁在别人家墙上, 那面墙塌了我就进不去了; 数据管道则是我自己接进来的, 想拔随时能拔.
>
> 这个授权是必要的, 因为 Vercel 确实需要在我的 GitHub 上建仓库读代码, 而两家是互不相干的公司, 需要我出面授权一次. 这是一次性的.

**深入解读**

> 一句话概括: 门和数据源要分开.
>
> 这个机制叫 OAuth, 它的设计目的正是让你能在不交出密码的前提下, 授予第三方有限的, 可随时撤销的访问权. 理解了这一点你会发现, 它和 "用第三方账号登录" 在风险结构上完全不同: 前者可撤销且不影响你的账号, 后者一旦断了你就进不去了.
>
> 溯源见 [03-deploy-your-first-app 的 "6. 授权 GitHub 这一步在做什么"](../03-deploy-your-first-app/README-cn.md).

## 10. 哪些改动需要后端参与

**问题**

> 下面几个改动, 判断哪些只动了静态内容, 哪些会让后端函数被调用: (a) 把页面底部的版权年份从 2025 改成 2026; (b) 用户点了一个按钮, 页面上显示出一句从服务器返回的话; (c) 换掉网站的 logo 图片; (d) 用户在搜索框输入关键词, 页面列出匹配的结果.
>
> 回答之前先回忆一下静态内容和动态内容的区别.

**考察点**

> 考你能不能在具体场景里分清这两类内容. 这个区分在排错时会直接派上用场, 因为它决定了你该去哪一侧找证据.

**参考回答**

> | 改动 | 类型 | 判断依据 |
> | :--- | :--- | :--- |
> | (a) 版权年份改成 2026 | 静态 | 谁看什么时候看都一样, 写死在代码里 |
> | (b) 点按钮显示服务器返回的一句话 | 动态 | 要向服务器请求这句话 |
> | (c) 换掉 logo 图片 | 静态 | 一张固定的图, 不因人因时而变 |
> | (d) 搜索关键词列出结果 | 动态 | 关键词交给后端查询再返回结果 |
>
> 动态内容的本质就是一个函数, 接收输入, 返回输出.

**深入解读**

> 这个区分在第 25 题会直接用上. Runtime Log 记的主要是**后端函数被调用时产生的东西**, 纯静态的页面请求基本不会在那里留下完整记录.
>
> 所以如果你的问题是 "logo 没显示出来" 这种纯静态问题, 去 Runtime Log 里翻是翻不到的, 那该去浏览器的开发者工具看. 反过来 "点了按钮没反应" 这种, 就该去 Runtime Log 找.
>
> 分不清这两者的人, 会在一个根本不可能有记录的地方反复找, 然后开始怀疑是不是自己哪里配错了.
>
> 溯源见 [03-deploy-your-first-app 的 "7. 网站等于静态内容加动态内容"](../03-deploy-your-first-app/README-cn.md).

## 11. 部署列表里每条都有自己的网址

**问题**

> 打开 Deployments 页面, 你会发现每一条部署记录都有自己独立的网址, 点进去各是各的内容, 互不影响. Vercel 为什么要这么设计?
>
> 回答之前先回忆一下 Deployment 这个概念, 尤其是它 "不可变" 那个性质.

**考察点**

> 考你理不理解不可变这个性质, 以及它带来的好处. 这是后面回滚, 对比, 排错好几道题的共同前提.

**参考回答**

> 因为每个 Deployment 都是网站的一个**完整实例**. 它不只是代码, 还包括构建好的前端文件, 后端函数, 运行配置, 依赖包, 整套东西打包冻结在某一个时间点上, 很像游戏里的存档.
>
> 这些实例是**不可变的**: 部署出来就固定在那儿了, 你不会去 "修改一个 Deployment", 你只会创建一个新的. 所以它们天然相互隔离, 各自有各自的网址, 一个挂了不影响另一个.
>
> 这么设计的好处是任何一个历史版本都随时可以打开验证, 也随时可以回去.

**深入解读**

> 不可变这个性质直接推出了两个很实用的结论.
>
> 一是每个 Deployment 都有自己独立的构建日志, 所以排查部署问题的第一步永远是先确定 "是哪一次部署出的问题", 详见第 24 题.
>
> 二是旧版本永远还在原地, 这就是回滚之所以可能而且很快的原因, 详见第 21 题.
>
> 溯源见 [04-deployment-environment-and-git-branch 的 "5. 什么是 Deployment"](../04-deployment-environment-and-git-branch/README-cn.md).

## 12. 一堆部署同时活着, 用户看到哪一个

**问题**

> 你的项目里现在有五六个 Deployment 同时存在, 每个内容都不一样. 那么一个普通访问者打开你的正式网址时, 凭什么看到的是其中某一个而不是别的?
>
> 回答之前先回忆一下 Environment 这个概念.

**考察点**

> 考你能不能把 Environment 理解成指针而不是容器. 这个误解很常见, 而且会让后面的规则全都对不上.

**参考回答**

> 因为有一张 Production 标签贴在其中某一个 Deployment 上. Environment 本质上是一个**指针**, 或者说一张贴在 Deployment 上的标签, 标签指向哪个实例, 对应的访问者就看到哪个实例.
>
> 它不是一个容器, 里面并没有装东西, 它只是指向.

**深入解读**

> 指针这个模型能解释很多现象.
>
> 比如为什么 "发布" 可以是瞬间完成的: 因为它只是把指针挪一下, 不需要重新构建或者搬运任何东西.
>
> 比如为什么回滚也可以是瞬间的: 因为旧实例还在原地, 把指针挪回去就行.
>
> 如果你把 Environment 理解成容器, 这些现象都会变得难以解释. 你会以为发布是 "把新代码搬进生产容器" 这样一个搬运过程, 那自然想不通为什么它能这么快.
>
> 溯源见 [04-deployment-environment-and-git-branch 的 "6. 什么是 Environment"](../04-deployment-environment-and-git-branch/README-cn.md).

## 13. 你和同事各开了一个分支

**问题**

> 你在 `feature-a` 分支上改东西, 同事在 `feature-b` 分支上改东西, 两人都提交了. 这时候会有几个 Preview? 几个 Production? 两人的改动会互相干扰吗?

**考察点**

> 考你有没有注意到 Production 和 Preview 在结构上根本不对等. 很多人笼统地说 "一个是线上一个是测试", 但说不出这个不对称, 说明理解停留在表面.

**参考回答**

> 会有两个 Preview, 各自独立, 互不干扰, 各有各的网址. Production 只有一个, 而且还是原来那个, 因为谁都没往 production branch 提交.
>
> 原因是这两者性质不同:
>
> | 维度 | Production | Preview |
> | :--- | :--- | :--- |
> | 是什么 | 一张**标签** | 一个**类别** |
> | 能有几个 | 全项目只有一张 | 同时可以有很多个 |
> | 怎么变 | 从原来那个 Deployment 上撕下来贴到新的, 这个动作就是发布 | 凡是不属于 Production 的部署自动归到这一类 |

**深入解读**

> 这种不对称是有道理的. Production 回答的是 "用户现在看到什么", 这个问题在任何时刻都只能有一个答案, 所以它必须唯一. Preview 回答的是 "有哪些正在验证中的版本", 这个问题天然可以有很多个答案.
>
> 补充一点: 同一个 Deployment 身上可以同时有多张标签. 你在 Preview 里测好了决定发布, Production 标签也会贴到这个 Deployment 上, 这时它既是 Preview 也是 Production, 内容当然完全一样, 因为本来就是同一个实例.
>
> 溯源见 [04-deployment-environment-and-git-branch 的 "6. 什么是 Environment"](../04-deployment-environment-and-git-branch/README-cn.md).

## 14. 让同事帮你复现一个 bug

**问题**

> 你在分支上发现了一个 bug, 把 Preview 网址发给同事让他看看. 同事说他那边一切正常. 期间你确实又推过一次代码. 问题出在哪? 应该发哪个网址?

**考察点**

> 考你知不知道 Preview 有两种网址, 以及它们的区别. 这是个很实用的细节, 不知道的人会在协作时反复出这种岔子.

**参考回答**

> 问题出在我发的是**跟着 branch 走的网址**, 它永远指向这个分支上最新的那次部署. 我在这期间推了新代码, 同事点开时看到的已经是新版本, bug 自然复现不了.
>
> 应该发**跟着 commit 走的网址**, 它死死钉在某一次具体的部署上, 不会变. 这样同事看到的就是我发现 bug 时的那个版本.

**深入解读**

> 这两种网址的区别本质上还是指针和快照的区别, 和第 12 题是同一套思路. branch 网址是个会移动的指针, commit 网址是个固定的快照.
>
> 选择原则很简单: 想让对方看 "这个分支现在什么样", 发 branch 网址; 想让对方看 "某个特定时刻是什么样", 发 commit 网址. 凡是涉及复现问题, 对比改动前后, 或者留证据, 都该用 commit 网址.
>
> 溯源见 [04-deployment-environment-and-git-branch 的 "6. 什么是 Environment"](../04-deployment-environment-and-git-branch/README-cn.md).

## 15. 你往 dev 分支提交了代码

**问题**

> 你在一个叫 `dev` 的分支上改完代码提交了. 你的用户会立刻看到这个改动吗? Vercel 是根据什么做出这个判断的?

**考察点**

> 这是整门课最该被答对的一道. 答不上来意味着你随时可能在不知情的情况下改崩线上.

**参考回答**

> 用户不会看到. Vercel 会自动部署一个 Preview, 但 Production 保持原样.
>
> 判断依据是**这次改动提交到了哪个 branch**. 默认规则是: 提交到 production branch (默认是 `main`) 就是 Production, 提交到其他任何 branch 就是 Preview.
>
> 所以往 `main` 提交, 用户立刻看到新内容; 往别的分支提交, 用户什么都察觉不到.

**深入解读**

> 这条规则的巧妙之处在于, 它把一个抽象的决定 (这次改动要不要发布给用户) 绑定到了一个具体且随时可见的事实 (我现在在哪个 branch 上). 你不需要在任何界面上做选择, 你只需要看一眼自己在哪儿.
>
> 也正因为如此, 这套流程里唯一真正危险的地方就是没确认 branch 就提交, 详见第 20 题.
>
> 溯源见 [04-deployment-environment-and-git-branch 的 "8. Branch 决定贴哪张标签"](../04-deployment-environment-and-git-branch/README-cn.md).

## 16. 新项目的主分支叫 master

**问题**

> 你换了个项目, 发现团队的主分支叫 `master` 不叫 `main`. 那么往 `master` 提交会触发 Production 部署吗? 你怎么确认?

**考察点**

> 考你有没有把上一题的规则背成教条. 只记住 "main 等于线上" 的人, 遇到这种情况会判断错.

**参考回答**

> 会不会取决于配置, 不能想当然.
>
> 哪个 branch 算 production branch 是**可以配置的**, `main` 只是默认值. 团队完全可以把 `master` 或者别的分支指定为 production branch.
>
> 确认方法是去项目设置里看 production branch 指的是哪个. 正确的理解是 "被指定为 production 的那个 branch 等于线上", 而不是 "main 等于线上".

**深入解读**

> 这道题考的其实是一种习惯: 接手一个新项目时, 先确认它的规则配置, 而不是套用自己熟悉的默认值.
>
> 这个习惯适用范围很广. 默认值之所以叫默认值, 就是因为它可以被改. 凡是 "默认如何" 的知识, 都该顺带记住 "这是可配置的" 以及 "去哪儿确认".
>
> 溯源见 [04-deployment-environment-and-git-branch 的 "8. Branch 决定贴哪张标签"](../04-deployment-environment-and-git-branch/README-cn.md).

## 17. 新项目第一次部署就直接上线了

**问题**

> 你新建了一个 Vercel 项目, 部署完成后发现它直接就是 Production, 网站立刻能公开访问, 并没有先给你一个 Preview 让你确认. 这正常吗? 为什么?

**考察点**

> 考一个容易踩的规则例外. 不知道的人会以为自己哪里配错了, 或者更糟, 以为自己在 Preview 里改东西其实改的是线上.

**参考回答**

> 正常. 规则是**一个新项目的第一次部署总是 Production**, 不管它来自哪个 branch.
>
> 第 15 题那套 Preview 规则, 要等第一个 Production 部署存在之后才开始生效.

**深入解读**

> 这条规则的设计意图说得通: 一个还没有任何 Production 部署的项目, 让第一次部署去当 Preview 是没有意义的, 因为根本不存在 "线上版本" 需要被保护.
>
> 实践上要注意的是, 这意味着**新项目的第一次部署是没有缓冲的**. 如果那份代码里有不该公开的东西, 它会立刻公开. 所以新建项目时, 第一次部署的内容值得先看一眼.
>
> 溯源见 [04-deployment-environment-and-git-branch 的 "8. Branch 决定贴哪张标签"](../04-deployment-environment-and-git-branch/README-cn.md).

## 18. 同事说发到 dev 环境看看

**问题**

> 同事让你 "把这个改动发到 dev 环境看看". 在 Vercel 的语境下, 他可能指的是什么? 你需要问清楚什么?

**考察点**

> 考一个很常见的误解: 以为 Vercel 提供了一个叫 "开发环境" 的在线环境. 这个误解会让你去找一个根本不存在的入口, 也会让沟通说不到点上.

**参考回答**

> 需要问清楚, 因为这句话在 Vercel 的语境下有歧义.
>
> Vercel 默认三个环境是 Local, Preview, Production, 但它们性质不对等. **Local 指的就是你自己的电脑**, 本地开发调试用, 根本没上传到 Vercel. 真正部署在 Vercel 上的只有 Preview 和 Production 两类.
>
> 所以同事可能指三件事之一: 在本地跑起来看看; 推一个分支出 Preview 看看; 或者他们团队买了 Pro 以上的计划, 配了一个叫 dev 的 Custom Environment. 这三件事完全不同, 得问清楚.

**深入解读**

> Custom Environments 是 Pro 和 Enterprise 计划的功能, 用来支持 staging, QA 这类更细的划分. Hobby 计划用不了, 就是 Preview 加 Production 两类, 对个人开发者完全够用.
>
> 这道题的实际价值在于: 团队协作时 "环境" 这个词是高频歧义源, 不同公司不同平台对它的定义都不一样. 养成确认的习惯, 能避免很多白做的工.
>
> 溯源见 [04-deployment-environment-and-git-branch 的 "7. Vercel 默认给你哪几个环境"](../04-deployment-environment-and-git-branch/README-cn.md).

## 19. 给一个有用户在用的网站加功能

**问题**

> 你的网站已经有人在用了, 现在要加一个新功能. 请按顺序说出完整的操作流程, 从动手到用户看到新版本为止. 这个流程里, 哪一步才算真正的 "发布"?

**考察点**

> 整套题的核心综合题, 把前面几道的概念串成一条可执行的流程. 后半问考你分不分得清 "改动" 和 "发布" 是两回事.

**参考回答**

> 流程是这样:
>
> 一, 从 `main` 开一个新 branch, 比如叫 `development`.
>
> 二, 在新 branch 上改代码并提交.
>
> 三, Vercel 自动检测到提交, 部署出一个 Preview. 这一步不需要我做任何事.
>
> 四, 打开 Preview 网址, 验证改动符合预期.
>
> 五, 确认没问题后, 在 GitHub 上发起 Pull Request, 把 `development` 合并进 `main`.
>
> 六, 合并的瞬间 Vercel 检测到 `main` 变了, 自动部署并更新 Production.
>
> 七, 用户看到新版本.
>
> 真正的 "发布" 是第五步那个**合并动作**. 在那之前所有的改动, 提交, 部署, 验证, 都不会让任何用户看到任何东西.

**深入解读**

> 这个流程的设计精髓在于, 它把风险**集中到了单个明确的动作上**. 你在前四步里怎么折腾都是安全的, 只有合并那一下是不可儿戏的. 这比 "每一步都有点风险" 的流程好管理得多.
>
> 另外注意整个流程里你在 Vercel 界面上一个按钮都没点. 第三步和第六步都是自动触发的, 依赖的正是第 6 题和第 7 题讲的那条 GitHub 到 Vercel 的链路.
>
> 溯源见 [04-deployment-environment-and-git-branch 的 "8. Branch 决定贴哪张标签"](../04-deployment-environment-and-git-branch/README-cn.md) 下的 "完整的工作流".

## 20. 这套流程里最容易出事的一步

**问题**

> 上一题那套流程, 每一步都不难. 但其中有一个地方一旦疏忽, 后果是直接改崩线上. 是哪里? 具体怎么防?

**考察点**

> 考你有没有真正动手做过. 只读不做的人答不出危险点在哪, 因为读的时候每一步看起来都一样平淡.

**参考回答**

> 最危险的是**提交前没确认自己在哪个 branch 上**.
>
> 因为按第 15 题那条规则, 提交到 production branch 就直接是 Production. 如果我以为自己在 `development` 上, 其实还在 `main` 上, 那这次提交就绕过了整个验证流程, 直接推给了所有用户.
>
> 防的办法是养成习惯: 在 GitHub 上改文件之前先看一眼分支选择器显示的是什么; 填提交信息时再确认一次选的是提交到当前分支, 而不是别的选项.

**深入解读**

> 这道题值得单独拎出来, 是因为这套流程的其他步骤都有容错. 分支建错了删掉重来就行, 代码改错了 Preview 里能看出来, 唯独提交到错误的分支这一下是没有缓冲的, 你按下去用户就看到了.
>
> 更一般地说, 任何流程里都值得找出这样的 "不可逆节点", 然后在那里放一道确认. 这比在每一步都小心翼翼有效得多, 也轻松得多.
>
> 溯源见 [04-deployment-environment-and-git-branch 的 "9. 练习"](../04-deployment-environment-and-git-branch/README-cn.md), 那里的每一步都在反复强调确认 branch.

## 21. 新版本上线后发现有问题

**问题**

> 你刚把一个改动合并到 `main`, Production 也更新了, 结果用户反馈新版本有问题. 你想尽快让网站回到上一个正常版本, 能做到吗? 为什么?
>
> 回答之前先回忆一下 Deployment 的不可变性和 Environment 的指针性质.

**考察点**

> 考你能不能把前面两个概念组合起来, 推出一个实际能力. 认为发布是 "覆盖" 的人, 会想不通回滚是怎么做到的.

**参考回答**

> 能做到, 而且很快.
>
> 因为旧版本哪儿也没去, 它还在原地. 发布不是覆盖, 而是移动一个**指针**: Production 这张标签从旧的 Deployment 挪到了新的 Deployment 上. 旧的那个 Deployment 依然完整地存在于部署列表里, 只是不再是 Current.
>
> 所以回滚就是把指针挪回去, 指向那个已知正常的旧 Deployment. 不需要重新构建, 也不需要重新上传代码.

**深入解读**

> 把第 11 题, 第 12 题和这道题连起来看, 是一条完整的因果链: 因为 Deployment 不可变, 所以旧版本永远还在; 因为 Environment 只是指针, 所以切换是瞬间的; 两者结合, 回滚就成了一个又快又安全的操作.
>
> 这也解释了为什么现代部署平台普遍采用这个模型. 在传统的 "把新文件覆盖到服务器上" 的模式里, 回滚意味着要把旧文件再传一遍, 慢, 而且容易出错.
>
> 实践上还要补一句: 回滚只是止血, 不是修复. 回滚之后仍然要回到分支上把问题真正改好, 再走一遍第 19 题那套正常流程发布.
>
> 溯源见 [04-deployment-environment-and-git-branch 的 "6. 什么是 Environment"](../04-deployment-environment-and-git-branch/README-cn.md).

## 22. 两种故障, 两个地方

**问题**

> 下面两个情况, 你分别该去看哪种日志: (a) 你提交了代码, 但网站上的内容没有任何变化; (b) 网站能正常打开, 但用户点提交按钮就报错.
>
> 说出你的判断依据.

**考察点**

> 排错的第一步永远是分类, 分错了类后面全是无用功. 这道题考的就是分类能力.

**参考回答**

> (a) 看 **Build Log**, (b) 看 **Runtime Log**.
>
> | 维度 | Build Log | Runtime Log |
> | :--- | :--- | :--- |
> | 记的是什么 | 部署过程 | 网站运行过程中后端函数被调用时发生的事 |
> | 什么时候看它 | 打不开, 或者内容没更新 | 打得开, 但某个功能不对 |
> | 挂在哪一级 | 某一次具体的 Deployment 上 | 项目级, 在项目的 Logs 入口下 |
>
> (a) 的内容没变, 说明新版本压根没成功部署上去, 常见原因是依赖装不上, 代码编译不过, 或者配置缺失. (b) 的网站能打开, 说明部署是成功的, 问题出在运行阶段.
>
> 判断依据就一句话: **网站打得开吗?**

**深入解读**

> 这个判据之所以好用, 是因为它只依赖一个任何人都能立刻观察到的事实. 你不用懂报错, 不用看代码, 打开浏览器试一下就知道该去哪儿.
>
> 表里那个 "挂在哪一级" 也不是随便设计的, 它源自第 11 题讲的 Deployment 隔离性: 每次部署有自己独立的构建过程, 自然也有自己独立的构建日志; 而运行是整个项目在持续进行的, 所以运行日志只能是项目级的.
>
> 溯源见 [05-view-logs 的 "6. 两种 Log: 部署时和运行时"](../05-view-logs/README-cn.md), 那一节末尾还有一张对照表.

## 23. 用户昨晚遇到的问题, 你今早才知道

**问题**

> 同事今天上午告诉你, 昨天晚上有用户反馈网站某个功能报错. 你现在去 Runtime Log 里查, 能查到吗? 这件事对你处理线上问题的方式有什么影响?

**考察点**

> 考一个有真实后果的事实. 不知道的人会在日志已经消失之后还在那儿翻找, 或者干脆错过排查窗口还不自知.

**参考回答**

> 查不到. Runtime Log 在 Hobby 计划**只保留 1 小时**, Pro 是 1 天. 昨晚的记录早就没了.
>
> 影响是: **运行时的问题必须当场查**. 发现异常立刻去看日志, 不要等. 如果靠自己发现不了, 就得想别的办法提前知道, 而不是指望事后翻日志.
>
> 顺带对比一下, Build Log 是**永久保存的**, 三个月前那次部署的构建日志随时能翻回去看. 两者差别很大.

**深入解读**

> 这道题的重点不是记住 "1 小时" 这个数字, 而是记住它带来的行为改变.
>
> 这也是个很好的例子, 说明为什么了解限制和了解功能同样重要. 一个只知道 "Vercel 有日志功能" 的人, 和一个知道 "我这个计划上运行时日志只留一小时" 的人, 面对线上问题时的反应速度完全不同.
>
> 如果项目确实需要长期留存日志, 那是升级计划或者配置 Drains 往外导的事情, 超出这门课范围, 但你要知道有这么个选项存在.
>
> 溯源见 [05-view-logs 的 "7. 这两种日志各能保留多久"](../05-view-logs/README-cn.md).

## 24. 想看三个月前那次部署出了什么事

**问题**

> 你想回头查一次三个月前的部署, 看看当时构建过程里发生了什么. 找得到吗? 具体怎么找?

**考察点**

> 和上一题构成对照, 考你分不分得清两种日志在保留策略上的差异. 顺带考你知不知道构建日志的入口在哪.

**参考回答**

> 找得到. Build Log 是永久保存的, 每一次 Deployment 的构建日志都一直留着.
>
> 找法是: 进入项目的 Deployments 页面, 在列表里找到那次部署的记录, 点进它的详情页, 展开 Build Logs.
>
> 关键是要先定位到**是哪一次部署**, 因为构建日志是挂在具体某个 Deployment 上的, 不是项目级的.

**深入解读**

> 这道题顺带巩固了一个心智模型: 日志的归属层级, 和它记录的东西是对应的.
>
> 构建是每次部署各干各的, 所以构建日志按 Deployment 归档, 永久留存, 因为每个 Deployment 本身就永久留存.
>
> 运行是整个项目在持续进行的, 所以运行日志是项目级的; 又因为量大, 只能保留一段时间.
>
> 溯源见 [05-view-logs 的 "7. 这两种日志各能保留多久"](../05-view-logs/README-cn.md), 以及同篇的 "练习 1: 进入一次具体的 Deployment".

## 25. Runtime Log 里什么都没有

**问题**

> 你在 Runtime Log 里翻了半天, 一条相关记录都找不到. 列举几种可能的原因.

**考察点**

> 考你知不知道这个工具的边界. 不知道边界的人会在错误的地方反复找, 浪费时间还怀疑是自己配错了.

**参考回答**

> 几种可能:
>
> 一, 时间范围筛选选得太窄, 或者事情发生在保留期之外 (Hobby 只有 1 小时).
>
> 二, 我触发的那个操作**根本没调用后端**. Runtime Log 记的主要是后端函数被调用时产生的东西, 纯静态的页面请求基本不会留下完整记录.
>
> 三, 问题本身就发生在浏览器一侧, 比如图片没加载, 样式错乱, 前端脚本报错. 这类问题服务端根本不知情, 该去浏览器的开发者工具里看.

**深入解读**

> 第二和第三条都要用到第 10 题的静态与动态之分. 能判断一次交互到底有没有触达后端, 你才知道该去哪一侧找证据.
>
> 这是排错里一个很常见的时间浪费点: 在一个根本不可能有记录的地方反复找, 然后开始怀疑是不是自己权限不够或者配置错了. 知道工具的边界, 能省掉这类内耗.
>
> 溯源见 [05-view-logs 的 "6. 两种 Log: 部署时和运行时"](../05-view-logs/README-cn.md) 中 Runtime Log 那一小节, 以及 "练习 3: 看 Runtime Log" 里提示看不到日志时该检查什么的部分.

## 26. 部署失败, 满屏英文

**问题**

> 你的部署失败了, 打开 Build Log 看到几百行英文, 完全看不懂. 接下来你会怎么做? 一步步说.

**考察点**

> 考这门课最核心的方法论能不能落到具体动作上. 也考你会不会给 AI 提供足够的上下文, 这是实际效果差异最大的地方.

**参考回答**

> 第一, 不需要自己读懂. 先从日志的**末尾往上读**, 因为部署失败时有用的报错几乎总在最后几行附近, 前面大多是正常的步骤记录.
>
> 第二, 把报错附近那一段和日志最后几十行复制出来.
>
> 第三, 连同上下文一起交给 AI. 上下文要包含五样: 现象的具体描述, 我对阶段的判断 (这是部署阶段的问题), 日志原文, 项目的技术栈, 以及我最近做过的改动.
>
> 第四, 按 AI 给的方案改, 然后重新部署验证.
>
> 提问时最好加一句: 如果日志信息不足以定位, 就直接说还需要什么, 不要猜.

**深入解读**

> 这门课的主张是: **你不需要自己看懂日志, 你只需要知道去哪儿找日志**. 因为分析错误日志恰恰是 AI 最擅长的事情之一, 那些堆栈信息和依赖冲突对人是天书, 对模型是它见过几百万遍的模式.
>
> 所以整个排错流程只剩四步: 判断阶段, 取出日志, 连同上下文交给 AI, 按方案改并验证. 这四步里只有前两步是必须你自己做的.
>
> 排错的瓶颈很少在 "分析", 多半在 "信息不全". 多花一分钟把上下文补齐, 能省下十轮来回追问.
>
> 溯源见 [05-view-logs 的 "10. 导师寄语"](../05-view-logs/README-cn.md), 以及 "练习 4: 把日志变成一段能用的提问" 里那段排错提问模板.

## 27. 部署显示成功, 网站却没变

**问题**

> Vercel 上这次部署的状态是 Ready, 一切正常, 但你打开网站发现内容还是老样子. 列举几种可能的原因, 以及你会按什么顺序逐个排除.

**考察点**

> 综合排查题, 没有单一答案. 考你能不能把前面学的几条规则组合起来, 系统性地缩小范围.

**参考回答**

> 几种可能, 按我会检查的顺序:
>
> 一, **我打开的网址不对**. 这次成功的部署可能是个 Preview, 而我打开的是 Production 网址. 去 Deployments 页面看那条记录标的是 Preview 还是 Production.
>
> 二, **我提交到了非 production 的分支**. 按 branch 规则, 那样只会产生 Preview, Production 当然不变. 这其实和上一条是同一个原因的两个面.
>
> 三, **我改的地方不对**. 去 GitHub 确认那次提交真的落在我以为的那个文件和那个分支上.
>
> 四, **浏览器缓存**. 强制刷新一下, 或者换个无痕窗口试试.

**深入解读**

> 这道题的价值在于示范一种排查顺序: **先怀疑自己看的地方不对, 再怀疑系统出了问题**.
>
> 前三条其实都指向同一件事, 就是 Production 和 Preview 搞混了. 这是新手最高频的困惑, 因为两个网址长得很像, 都能正常打开, 内容却不一样.
>
> 一个很实用的习惯: 遇到 "改了没生效" 的情况, 第一件事是去 Deployments 页面看那条记录到底标的是什么, 而不是反复刷新网站.
>
> 溯源见 [04-deployment-environment-and-git-branch 的 "8. Branch 决定贴哪张标签"](../04-deployment-environment-and-git-branch/README-cn.md), 以及同篇的 "练习 5: 对比 Preview 和 Production".

## 28. 界面上找不到教程说的按钮

**问题**

> 你照着一份教程操作, 但界面上根本找不到它说的那个按钮. 你会怎么做? 需要给 AI 提供哪几样东西?

**考察点**

> 考遇到信息过期时的应对方式, 这是自学能力的核心. 也考你会不会给 AI 足够的上下文.

**参考回答**

> 先意识到这是正常现象, 不是我做错了, 而是平台改版了. 不要在那儿反复找.
>
> 然后截一张当前界面的图, 连同三样东西一起发给 AI: **截图** (我现在看到什么), **教程原文** (我本来该看到什么), **我的目标** (我想做成什么).
>
> 让它告诉我这个功能现在在哪, 该点哪里, 一步步说. 如果功能已经改名或者被去掉了, 让它直接说并给出替代做法.
>
> 最后加一句: 如果它也不确定, 就告诉我该查官方文档的哪一页, 不要猜.

**深入解读**

> 那三样信息缺任何一样, AI 都只能瞎猜. 只发截图它不知道你想干什么, 只发教程原文它不知道你的界面长什么样.
>
> 最后那句 "不要猜" 是个很实用的技巧. AI 在不确定的时候有时会编一个听起来很像那么回事的路径, 明确要求它承认不确定, 能显著降低这种情况.
>
> 把这道题和第 26 题放在一起看, 你会发现它们是同一个动作的两个场景: 界面找不到就截图问, 功能坏了就取日志问. 底层都是**找到证据, 交给能处理它的人**.
>
> 溯源见 [01-why-vercel 的 "9. 截图会过期, 但逻辑不会"](../01-why-vercel/README-cn.md), 完整的 prompt 就在那一节的代码块里.

## 29. 把项目交接给别人

**问题**

> 你要把一个部署在 Vercel 上的项目交给同事接手. 除了账号权限, 你需要带他认哪几个关键位置, 分别是干什么用的? 另外要交代他什么工作流程?

**考察点**

> 综合题, 考你脑子里有没有这个系统的完整地图. 说得出地图的人才算真的会用, 只会按固定步骤操作的人说不全.

**参考回答**

> 至少这几个位置:
>
> | 位置 | 干什么用 |
> | :--- | :--- |
> | GitHub 仓库 | 唯一真相来源, 要改任何内容都在这里改. 顺带告诉他 production branch 是哪个 |
> | Deployments 页面 | 看所有部署记录, 每条标着是 Production 还是 Preview, 状态如何, 来自哪个分支哪次提交. 排查 "改了没生效" 从这里开始, 回滚也在这里 |
> | 某次 Deployment 里的 Build Log | 部署失败时来这里找原因, 永久保存 |
> | 项目级的 Logs 入口 | 运行时出问题来这里, 但要提醒他保留期很短, 得当场查 |
> | 用量页面 | 看离额度上限还有多远 |
>
> 流程上要交代清楚: 改东西先开分支, 在 Preview 上验证, 确认后合并进 production branch 才算发布. 提交前务必确认当前在哪个分支.

**深入解读**

> 这道题其实是在问: 你有没有把这门课学成一张地图, 而不是一串步骤.
>
> 区别在于, 记住步骤的人只能沿着教过的路径走, 一旦情况变了就不知所措; 有地图的人知道每个部位是干什么的, 遇到没见过的情况也能推断该去哪儿.
>
> 检验方法很简单: 如果你能把上面每个位置和 "它回答什么问题" 一一对应起来, 那你就有地图了. Deployments 回答 "现在线上是哪份代码", Build Log 回答 "部署为什么失败", Logs 回答 "运行时发生了什么", 用量页面回答 "我还能用多少".
>
> 溯源见 [03-deploy-your-first-app 的 "练习 2: 认一遍项目控制台"](../03-deploy-your-first-app/README-cn.md), 以及 [05-view-logs 的 "11. 速查"](../05-view-logs/README-cn.md).

## 30. 这套机制你其实早就见过

**问题**

> Vercel 的 Preview 加 Production 这套机制, 和 Git 的分支加主干这套机制, 你觉得它们之间是什么关系? 想想你平时是怎么用 Git 分支的.

**考察点**

> 全套题里最开放的一道, 考你能不能跨层级识别同一个模式. 能答出来的人, 学任何新工具都会明显更快.

**参考回答**

> 它们解决的是同一类问题, 只是作用的层面不同.
>
> Git 分支让你在不影响主线代码的前提下安全地尝试新想法, Environment 让你在不影响用户的前提下安全地测试新部署.
>
> Git 管的是**代码的版本**, Environment 管的是**整个运行中系统的版本**.
>
> 但核心逻辑完全一样: 创建一个隔离的空间, 在里面放心大胆地试, 确认没问题再合并到主线.

**深入解读**

> 认出这个模式的实际好处是, 你学 Environment 的时候不是在记一套全新的规则, 而是在把一套已经熟悉的思路挪到一个新的层面上. 这也是为什么这两个概念一旦想通就再也不会忘.
>
> 这个模式还远不止用在技术上. 设计师在 Figma 里有版本历史, 写文档的人用修订记录, 你自己存 PPT 也会存 v1 v2 v3. 底下都是同一个问题: 我想改, 但我不想搞砸现有的东西. 解法也永远是同一个: 复制一份, 在副本上改, 改好了再替换.
>
> 以后你换到别的部署平台, 可以直接用这个模式去找对应的机制: 它的 "隔离空间" 叫什么, 它的 "合并到主线" 是哪个动作. 找到这两个, 基本就上手了.
>
> 溯源见 [04-deployment-environment-and-git-branch 的 "11. 导师寄语"](../04-deployment-environment-and-git-branch/README-cn.md).
