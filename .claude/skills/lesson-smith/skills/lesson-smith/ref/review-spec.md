# 统稿规范

各篇 mini task 是分头写出来的, 合起来未必是一条线. 这一步通读全系列, 把它变成一条线.

适用范围: readup, upskill, showcase 三类通用. 位置在最后一篇 mini task 写完之后, 写全局中文之前.

**为什么单独一步**: 后面几步都拿 examples 当稳定素材 (系列索引要梳理它们, 根 TICKET 要从它们萃取关键能力, 英文重写要给它们定统一术语). 素材本身还在漂的时候做这些, 全是白做. 这一步是主干成文的判据.

**为什么建议开新 session**: 它要通读全部 mini task, 而写作阶段留下的上下文 (讨论过的取舍, 改过又改回去的段落) 只会挤占注意力. 拿一个干净的上下文读成品, 看到的东西不一样.

---

## 1. 只读中文, 别碰英文

这一步跑在英文重写之前, 所以 repo 里应该只有 `-cn.md`. 如果有存量英文文件, 不要读也不要改, 它们会被重写那一步整体覆盖.

---

## 2. 通读, 然后找五类问题

按编号顺序把 `examples/*/README-cn.md` 与 `examples/*/TICKET-cn.md` 从头读到尾. 一次读完再动手改, 不要边读边改: 第 3 篇的问题往往要读到第 8 篇才认得出来.

**术语与命名不一致.** 同一个概念在不同篇里叫了不同的名字, 或者同一个名字在不同篇里指了不同的东西. 这是最常见也最伤的一类, 因为学生会以为那是两个东西.

**深浅与风格漂移.** 前几篇是试水时写的, 后几篇是熟练之后写的, 中间往往有一道坎: 篇幅忽长忽短, 假设的前置知识忽深忽浅, 讲解的颗粒度对不上. 以定稿的风格为准往回统一, 不是以第 1 篇为准.

**承上启下断掉.** 每篇开头该接住上一篇留下的东西, 结尾该给下一篇铺路. 分头写的时候这些接口最容易缺失, 读起来就是一堆独立文章而不是一门课.

**前后矛盾.** 同一件事在两篇里给了不同的说法, 或者前面说"后面会讲"而后面没讲, 或者后面用到了前面没交代过的东西.

**遗漏.** 规划里 (`examples/_lm-example-plan.md`) 说要覆盖的东西, 实际写的时候漏掉了. 拿 plan 和成品对一遍.

顺带核对 README 与 TICKET 的成对关系: 每个 mini task 的 TICKET 的 "要做的事情" 要呼应它 README 的练习与操作步骤, "检查清单" 要呼应学习目标. 改了 README 而 TICKET 没跟上, 是写作阶段的典型欠账.

---

## 3. 改法

**列出来给创作者过目, 再动手.** 把找到的问题按上面五类分组列出来, 每条给出在哪篇, 什么问题, 打算怎么改. 术语类的要点明打算统一成哪个, 因为那是创作者的口味. 他点头之后再改.

**成批改, 不要一篇篇过.** 术语统一这类跨篇的改动, 一次改完全部出现的位置, 别改一篇算一篇.

**改完复读被改动的段落.** 尤其是术语替换, 换完之后句子常常读起来别扭, 因为原来那个词是句子长出来的骨架.

---

## 4. 什么时候算过

三条都满足才进下一步:

- 上面五类问题都过了一遍, 找到的都改完或经创作者明确决定不改.
- 从头到尾读下来是一条线, 不是一堆独立文章.
- 创作者本人点头说主干可以了.

第三条不能省. 这一步的判据里有大量口味成分, 不是 AI 能单方面宣布通过的.
