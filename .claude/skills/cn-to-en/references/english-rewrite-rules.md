# 中文文档改写英文: 共用规则

这份文件是 cn-to-en 流程里所有环节 (草稿, 审阅, 打磨, 统稿) 共用的裁判标准.
A 节是红线, 违反就是错. B 节是审阅环节的病症清单. C 节是打磨环节的授权范围.

---

## A. 硬性不变量

这几条无论哪个环节都不能破. `scripts/check_invariants.py` 会机械地查其中大部分.

1. **Header 结构不变.** Header 的数量, 层级 (`#` 的个数), 先后顺序必须与中文原稿逐一对应.
   只有标题文字换成英文. 不新增 header, 不删 header, 不升级降级, 不合并拆分.
2. **代码块不增不删.** Fenced code block 的数量, 顺序, 以及围栏后面的语言标记
   (```` ```python ````) 与原稿一致. 代码正文逐字保留. 唯一允许改动的是代码里的中文注释和
   中文字符串字面量, 可以改写成英文, 但不要顺手 "优化" 代码本身.
3. **表格不增不删.** 表格的数量, 顺序, 行数, 列数与原稿一致. 只翻译单元格里的文字.
4. **引用块不增不删.** Markdown quote (`>` 开头的块) 的数量与顺序与原稿一致.
5. **不许出现破折号.** 禁止 `—` (em dash), `–` (en dash), 以及 ` -- ` 这种当停顿用的双连字符.
   需要停顿就用逗号, 句号, 冒号, 括号, 或者干脆拆成两句. 命令行参数里的 `--flag` 不在此列.
6. **全文 ASCII 标点.** 不留全角逗号句号, 不留中文引号书名号, 不留 `…`.
7. **不留中文字符.** 正文和代码注释里都不应该再有汉字.
8. **链接与图片目标不变.** URL, 相对路径, 锚点原样保留. 只改 link text.
9. **不增不减信息.** 不添加原文没有的例子, 数字, 结论, 免责声明; 也不因为 "英文里显得啰嗦"
   就把原文的某个要点整段丢掉.

## B. 病症清单: 什么叫 "中文造成的英文不自然"

审阅环节按这份清单逐节扫. 一条 finding 要同时满足两点才值得列出来:
英文读着别扭, **并且** 别扭的根源看得出来是中文句式.
单纯的用词偏好 (British vs American, 同义词更换) 不算.

### B1. 句子骨架层面

- **话题句直译.** 中文爱用 "关于 X, ...", "对于 Y 来说, ..." 起头,
  直译成 `As for X, ...` / `For Y, it is ...`. 英文应该让 X 直接当主语.
- **一句中文 = 一句英文.** 整节句子长度均匀, 全是中等长度的陈述句, 读起来像节拍器.
  英文靠长短交替产生节奏, 该有的短句 (五到八个词) 一句都没有就是信号.
- **主语是抽象名词.** `The readability of the code is improved` 而不是
  `The code becomes easier to read`. 中文名词化倾向直接搬过来的结果.
- **of 链条.** `the configuration of the behavior of the parser`, 三个 of 串一起,
  是 "的" 字链的直译. 英文用复合名词或所有格拆开.
- **被动语态过量.** 中文常省略施事, 直译时习惯性用被动. 英文技术文档里主动语态是默认.
- **状语堆在句首.** 中文把时间, 条件, 目的一律前置, 英文常常后置更顺.
- **缺显式衔接.** 中文靠语序和语义黏合, 英文段落内句与句之间需要指代和衔接词才不散.
  反过来也算病: 每句都挂 `therefore` / `thus` / `so that` 是过度补偿.

### B2. 词汇与短语层面

- **四字并列直译.** "简单方便" 变成 `simple and convenient`, "安全可靠" 变成
  `safe and reliable`. 英文里这种同义并列是废话, 挑一个更准的词就够.
- **计量虚词.** `very`, `quite`, `greatly`, `fully`, `deeply` 这类程度副词密度过高.
- **套话动词.** `plays an important role in`, `can be regarded as`, `serves as a`,
  `is of great significance`, `we can see that`, `it is worth noting that`.
- **In order to.** 绝大多数场合 `To` 就够了.
- **序号词直译.** "首先 / 其次 / 最后" 变成 `Firstly, Secondly, Finally`.
- **翻译腔标志词.** `delve`, `leverage`, `robust`, `seamless`, `comprehensive`,
  `crucial`, `essentially`, `holistic`, `utilize`. 出现即可疑.
- **冠词.** 中文没有冠词, 直译最容易漏 `a` / `the`, 或者该用零冠词的地方多加一个.
- **时态单一.** 中文没有形态时态, 直译容易全篇一般现在时. 讲历史沿革,
  讲某次实验结果, 讲将来计划时应该换时态.
- **人称摇摆.** 一会儿 `we`, 一会儿 `you`, 一会儿无人称被动. 全文要统一.

### B3. 段落与篇章层面

- **每段都是总分结构.** 中文段落习惯先来一句总起, 再展开. 整节每段都这样就很假.
- **信息顺序照抄中文.** 中文先铺垫再给结论, 英文技术写作常常先给结论再解释.
  这一条是最值得整段推倒重写的信号.
- **过渡段空转.** 中文喜欢写 "接下来我们看看 XXX", 英文里这种句子多半可以删掉,
  header 本身就是过渡.
- **举例位置.** 中文 "比如说" 常挂在句尾补充, 英文一般把例子提到能支撑论点的位置.
- **括号补充过多.** 中文原稿的括号注释直译过来会打断英文句子的呼吸.

### B4. 保真类问题

这一类不是自然度问题, 但发现了也要记, 单独归为 F 类:

- 中文有的要点, 英文里丢了.
- 英文里冒出中文没有的断言, 数字, 例子.
- 术语前后不一致 (同一个概念在不同小节用了不同英文词).
- 专有名词, 产品名, API 名被误译 (这些应该原样保留).

## C. 打磨环节的授权范围

打磨环节唯一的目标是**英文读起来像英语母语技术作者原创的**, 不是 "把意见逐条打上补丁".

### 可以做

- 在同一个 header 之内, 信息可以任意重排. 中文原文按 1, 2, 3 的顺序讲三件事,
  英文第一句可以讲 2 和 3, 第二句讲 2 和 1.
- 合并段落, 拆分段落, 合并句子, 拆分句子.
- 把一整节的散装内容推倒, 用英文重新组织一遍.
- 删掉空转的过渡句, 删掉同义反复的半句话.
- 换比喻的落点, 只要传达的技术含义不变.

### 不可以做

- 跨 header 搬运内容. 重排只在一个 header 的辖区内进行.
- 违反 A 节任何一条.
- 增加原文没有的信息, 或者丢掉原文有的要点.
- 因为 "意见里没提" 就放过明显别扭的句子.

### 失败模式

这个环节最常见的失败是**逐条打补丁**: 拿着意见列表, 一条一条找到对应的句子做局部替换.
这样改完每个句子都合格了, 整段还是中文的骨架. 正确做法是先把一节的所有意见读完,
然后把整节当成一个待写的东西, 用英文重新写一遍, 顺手把意见都吃掉.

## D. 术语与格式约定

- 技术术语保留英文原样, 不要为了 "全英文" 把已经是英文的东西再改写一遍.
- 代码标识符, 文件名, 命令用反引号包起来, 与原稿一致.
- 加粗和斜体保留原稿的语义意图, 但不必逐一对应位置. 中文靠加粗断句的地方,
  英文常常不需要加粗.
- 列表项保持并列结构 (parallelism): 要么全是动词开头, 要么全是名词短语, 不要混.
- Header 文字用 sentence case 还是 Title Case, 全文统一, 跟着仓库既有英文文档的习惯走.
